> 讨论汇总日期：2026-11-07
>

## 1. 讨论范围

把 Skill 体系融入既有助手工作流时，实际碰到五类问题：

1. 两套证据链并存，口径与命名都需要收敛（§2）；
2. 用户能力层与内部执行层的边界要写死，否则机器契约会被复制到多处（§3）；
3. 混合表达的交互口径（§4）；
4. 内部执行机制对用户不可见（§5）；
5. 一批待决问题没有答案，先记账不动手（§6）。

## 2. 两套证据链的现状（总览 §7.2）

当前至少存在两套证据实现，各有来路与用途：

```
collect_evidence → assistant.skills.pipeline   （证据研究能力用，只读取证三技能）
verify_claim     → RumorAgent → rumor.evidence （事实核查能力用，七路分析 + 风险分）
```

现状盘点：

- `assistant.skills.pipeline`：本次新建的只读取证流水线（领域识别 → 信源发现 → 证据
  检索 → 去重 → 确定性报告），输出可定位引文 + 关系枚举 + 审计/预算，不建档、不评分。
- `rumor.evidence`：谣言 Agent 的联网证据本，产出 domain_tier 五级信源分级与立场，
  供 verdict 纯函数推导风险分，链条末端连着档案写入。

两套的关系目前只是"并存"，没有共享输出协议：主张形状、证据字段、关系枚举、
状态取值都各自定义。同名不同源也造成阅读干扰——`rumor/evidence.py` 与
`assistant/skills/pipeline.py` 都导出 `collect_evidence`，文档与代码审查时必须写全
模块路径才能指清是哪一个。

预期方向（总览 §7.2 建议）：**先统一用户目标和输出边界，不立即重写两套证据引擎**。
即先让"面对用户时承诺什么、不承诺什么"一致（不判真假、引文可定位、降级可见、
数值评分不展示），引擎层面维持双轨，等边界稳定后再评估是否合并。

## 3. 用户能力与内部执行分层（总览 §6 vs §5）

已取得的共识：

- 面向用户收敛为四个用户能力 Skill：事实核查 claim-checking、证据研究
  evidence-research、话题理解 topic-understanding、言论理解 speech-understanding，
  文档位于 `src/mylocalai/assistant/capabilities/`。（2026-11-20 已扩为八项，
  见本文件 §8 回流记录。）
- 取证三技能（domain / sources / evidence）是**执行阶段**，不新建第五种用户能力；
  对话跟进是横向助手政策，不是 Skill。
- 分层写作方式固定：capabilities 下的 SKILL.md 只写人读的能力策略（典型表达、覆盖
  工具、硬门禁、输出契约、降级、边界案例）；机器可执行契约（id/版本/输入 schema/
  计划步骤/预算/权限）的唯一规范来源是 `assistant.registry` 注册表 +
  `assistant/skills/pipeline.py`（规格 §2 防双维护）。

暴露过的问题：早期讨论里"能力版本、计划步骤、预算"同时出现在能力文档与注册表两处，
出现过口径漂移；现已收敛为单一规范来源 + parity/contract tests 校验的方向。

## 4. 混合表达处理（总览 §6.3）

一句话同时要求"核查真假"和"解释热度"时，路由**不拼接工具**，而是回一句自然话术让
用户选先看哪个。总览给出的原话：

> "我可以先帮你核查这条说法，也可以再补充它为什么受到关注。你希望我先核查真实性，
> 还是两部分一起看？"

方向上的注意点：这句追问不是 clarify 兜底，而是显式登记的复合能力交互；复合能力
按合同自动执行并持久化 composite_id/version，不得自由拼工具（规格 §1/§3.2）。

## 5. 内部机制不暴露（总览 §7.1）

以下内容是内部实现机制，不暴露给用户，也不作为用户可见状态：

```
task-intake / task-plan / task-finalize / preflight / postflight / commit
```

用户可见的只是中文能力名与自然语言状态（"核查中/整理中/已取消"），progress 事件
不展示内部 Skill 名与审计详情（规格 §8）。文档与话术写作时统一遵守这条，
`assistant/prompts.json` 的对外话术不得引用内部机制名。

## 6. 待决问题清单

按优先级排列，均未定案；每条注明为什么现在定不了。

| # | 待决问题 | 背景 | 卡在哪 |
|---|---|---|---|
| 1 | **事实核查 Skill 是否统一输出协议**：复用 RumorAgent 内部证据链（rumor.evidence），还是与取证三技能统一输出协议与边界规则 | 总览 §7.2；两套引擎主张/证据/状态定义不同 | 需要先明确"用户侧承诺"的验收标准，再动引擎 |
| 2 | 同名导出 `collect_evidence` 的歧义治理：rumor.evidence 与 assistant.skills.pipeline 各有一个，对外文档、错误信息、测试命名如何指清 | 现实代码即如此；审查时易误读 | 与问题 1 联动，统一协议时一并处理 |
| 3 | 用户能力版本与注册表的 parity 校验范围：哪些字段必须 contract tests 逐项比对（id/版本/输入 schema/预算/权限/结果 schema） | 规格 §2 要求唯一规范来源 + parity tests | 需要先列出注册表字段全集 |
| 4 | 混合表达的追问话术是否外置到 prompts.json（键位与多语言扩展） | 总览 §6.3 只有一句示例话术 | 话术定稿权在作者；需确认是否值得占键位 |
| 5 | read_opinions / deep_read / insights 等章节与画像工具的归属：算话题理解能力的步骤，还是横向对话跟进机制 | 总览 §6.2 只列了跟进话术，没列工具 | 需要先定义"能力必经步骤"与"横向可用"的判定规则 |
| 6 | collect_evidence 进入 tool_allowlist 后，`max_tool_calls_per_turn`（现为 2）是否够用：证据研究 + 搜索要不要各占一格 | assistant_rules.json 现值 2；重成本工具单轮可能只需 1 次 | 需要实测慢车道的用户中断率再调 |

## 7. 下一步建议

1. 先把问题 1 的"用户侧承诺清单"写出来（不判真假、引文可定位、降级可见、评分不展示、
   取消与预算耗尽保留部分结果），作为两套引擎共同遵守的边界；
2. 问题 2/3 随注册表接线落地时一并做 parity 测试；
3. 问题 4-7 不阻塞当前实现，记账待作者拍板。

## 8. 2026-11-20 已决（回流记录）

以下条目已由作者拍板并实施（分支 `feature/info-collection-skills`），与上文待决清单
相关的第 6/7 条口径一并落地：

- **新增两个只读对话能力**：`information-collection`（资料收集，工具
  `collect_research`）与 `authority-verification`（权威核验，工具
  `verify_authority`）。均为 permission=read：不建档、不出真假结论、不给数值评分；
  用户能力由六项扩到八项，《Agent工作流规格-v0.1.md》§1.1/§2/§9 已同步，能力文档在
  `src/mylocalai/assistant/capabilities/` 下，实施口径见
  `docs/信息收集与权威核验技能-2026-11-20.md`。
- **动态权威发现开放**（待决清单之外的新决策）：目录外候选只有官方/国际组织/学术/
  标准/事实核查类才尝试动态核验，且至少两类代码信号（官方后缀、已读正文里的官方标记、
  已核验页面正文里由代码抽出的直链、≥2 个独立已核验来源的交叉提及）；`session_verified`
  仅本次运行有效、不写回信源目录，作决定性证据还需交叉佐证；页面自称权威、模型说
  "匹配"都不算信号。
- **"1+3"输出口径**：有决定性来源的支持/反驳证据时才写"权威资料可以证明/直接反驳"；
  否则只能说"不能据此证明/反驳"或"没有找到"；证据互相冲突时说"既不能证明也不能反驳"；
  不设固定真假标签、不给数值评分，倾向（lean）不能单独升级为证明或反驳。
- **与材料分析/领域监测的分流**：一次给多条材料要批量核查 → 引导到 analyst 工作区的
  材料批次面板；要订阅领域、持续盯新消息 → 引导到 monitor 工作区的领域监测面板；
  对话里一句话导流，不拼工具、不新开 action（规格 §1.3）。
- **两能力同样不建档**（回应待决清单第 7 条的保存诉求）：想要可保存、可复看的结论，
  统一导流到事实核查能力（verify_claim，write + 档案）；只读两能力返回
  `dossier_id=None` + `not_saved=True`，用户也无法通过消息让它保存。
