# 修复说明（2026-10-15）

本文件记录针对 `docs/检验报告-2026-10-14.md` 提出的 14 项优化方案所做的代码改动、
当前验证状态，以及未能彻底解决的部分。逐条对应报告第 5 节的编号。

## 一、判定口径与信源名单外置（报告建议 1、2、13）

**改动**：新增 `rumor_agent/rules.py`（配置加载器）、`rumor_agent/verdict_rules.json`（阈值/封顶/
抬分锚点/稳定性护栏）、`rumor_agent/sources_registry.json`（信源 5 级名单、官方/非官方站名表）。

- `rumor_agent/verdict.py` 的 `NO_CLAIM_RISK_CAP`、`THRESHOLD_HIGH/SUSPECT/DOUBT`、
  证据抬分锚点（原 `78`/`58`）现在都从 JSON 读，模块常量只是当前值的快照。
- `rumor_agent/sources.py` 的 `_register(...)` 硬编码域名表删除，改为从
  `sources_registry.json` 摊平成 `_DOMAIN_TIERS`；`OFFICIAL_SITES`/`COMMERCIAL_SITES` 同源。
- 支持 `RUMOR_RULES_PATH` / `RUMOR_SOURCES_PATH`（整套替换）与
  `RUMOR_RULES_EXTRA_PATH` / `RUMOR_SOURCES_EXTRA_PATH`（增量：字典深合并、列表取并集）。
- 配置坏掉（文件缺失、JSON 语法错、根节点不是对象）只退回内置默认值并在
  `rules.load_warnings()` 里留原因，判定链路不受影响。
- **补全英文主流源**：名单加入 `bbc.co.uk`、`nytimes.com`、`washingtonpost.com`、
  `nature.com`、`sciencemag.org`、`nih.gov`、`europa.eu`（报告复核意见指出原名单只有
  `bbc.com`，`bbc.co.uk`/`nytimes.com` 会被降为"未知来源"）。
- **文档与实现统一**：`source_kind()` 的 docstring 明确写出第三个返回值
  `UNKNOWN_KIND`（默认"其他"），并说明抗伪装靠的是"判不到官方"而不是"写成非官方"。

**验收**：改 `verdict_rules.json` 的 `thresholds.high` 为 50，同一输入立刻换档，未改一行 Python；
增量文件里加一个官方域名后 `classify_domain` 能识别且不破坏原名单。见
`tests/test_stability_config.py::TestRulesAreConfigurable`（6 个用例）。

## 三、稳定性：同输入结论可复现（报告建议 5、6）

先做了一次实测定位：**该提供方忽略 `seed`** —— 同 seed 连调 6 次，`aggression_level` 得到
5 种输出（含 `针对事件/中`、`针对群体/高`、`针对事件/高` 等）。所以报告建议 6
"调用时传 seed"在这家供应商上无效，只能在调用侧与下游挡。

**改动**：

1. **进程内结果缓存**（新增 `shared_core/llm_cache.py`）：以
   (提供方, 地址, 模型, system prompt, user text, temperature, max_tokens) 为键，
   同样的请求只真正调用一次；并发相同请求走 single-flight。只缓存成功结果，失败不缓存。
   `LLM_CACHE_TTL_S`（900）、`LLM_CACHE_MAX`（256，设 0 关闭）。
   这是"同输入结论可复现"的真正保证：重复分析复用同一份组件结果，而不是重新抽一次样。
2. **情绪分分桶**（`verdict_rules.json` 的 `stability.emotion_score_bucket=2`）：报告实测到的
   抖动是 `emotion_score` 8.0↔9.0，归并到最近 2 分倍数后两者同分，不再跨 45 分阈值
   （原 7.0→44 存疑、8.0→46 疑似）。分桶只作用于**计分**，与 `core_judge` 逐条等价的
   `speech_tier` 仍用原始分。

**验证对比**（`harness.py determinism --repeat 5 --level 4`，4 条文本）：

| 配置 | 不稳定字段 |
| --- | --- |
| 关闭缓存（`LLM_CACHE_MAX=0`，等价修复前） | `rumor`：`aggression`=[中,高]、`conclusion`=[疑似情绪化谣言,高度疑似水军]；`insult`：`emotion_score`=[10.0,9.0]；`rational`：`fallacy`=[以偏概全,未知,诉诸权威]；`review`：`emotion_tendency`=[未知,积极宏观] |
| 默认（缓存开启） | 4 条文本 × 7 个字段全部一致，分数极差 0.0 |

**残留限制**：分桶步长 2 必然还有别的边界（9.0↔10.0 仍可分），单靠分桶不能完全消除；
真正兜底的是缓存。而缓存是**进程内**的——重启服务后第一次分析仍可能落在另一档，
这一点不改变（报告发现 4 的成因是上游非确定性，工程侧只能收敛、无法根除）。

## 四、抗压性（报告建议 9、10、11）

**改动**：

1. **请求级时长预算**：`llm_cache.deadline_scope()` 让一次分析内的所有 LLM 调用共享总预算；
   每次 HTTP 尝试的超时取 `min(LLM_TIMEOUT_S, 剩余预算)`，预算用尽立刻返回错误转降级。
   `core_judge.judge()` 包在预算里（`JUDGE_DEADLINE_S`，默认 120 秒），
   `RumorAgent.analyze()` 同样包在自己的 deadline 里。
2. **网站并发上限**：`my_website/app.py` 加应用层并发闸门（默认 4 个在跑的分析），
   超出的请求立刻返回 503 + `Retry-After`，而不是堆在框架线程池里把
   `/api/health`、`/api/history` 一起堵死。
3. **`/api/health` 不碰大模型链路**：上游挂掉或名额占满时它仍能立刻回话，
   并回报 `active_analyses`、`analyze_budget_s`、缓存统计。
4. **前端可中断**：分析中显示"取消分析"按钮（`AbortController`）。
5. **超时线程真正停下**：`rumor_agent/agent.py` 不再用
   `ThreadPoolExecutor + shutdown(cancel_futures=True)`（那个不会打断运行中的 future），
   改为 daemon 线程 + `Event.wait(timeout=deadline)`；超时即
   `state.cancel()`，`AnalysisState.ensure()` 见到取消标记就不再开算新组件——
   残留的工具调用不会再发起 LLM/联网请求（Python 无抢占式中断，故为"协作取消"）。

**验收**：`TestRequestBudget`（5）、`TestConcurrencyCap`（3）、`TestAgentCancellation`（3）。
其中一条用不可达上游实测：`judge(text, deadline_s=3.0)` 在预算内降级返回而非挂满几分钟。

## 六、检验器自身（报告建议 7、8）

- **两条假阴性判据修正**（`.tmp/verify/harness.py`）：
  - 枚举回退判据原断言 `emotion_tendency in _EMOTION_TENDENCY_ENUM`，而"未知"本就是
    刻意设在白名单外的哨兵。现改为断言"落在白名单 ∪ 哨兵"，并同时暴露
    `LM._EMOTION_TENDENCY_DEFAULT` / `LG._FALLACY_SENTINEL` 供检查。
  - 信源抗伪装判据原要求 `kind.startswith("非官方")`，而抗伪装的真实属性是
    **"不得被判为官方"**。现改为 `not kind.startswith("官方")`
    （注意不能用 `"官方" in kind` —— "非官方（权威媒体）"里也含"官方"二字，这是本次踩到的坑）。
  - 哨兵值在源码里显式命名（`_EMOTION_TENDENCY_DEFAULT`、`_FALLACY_SENTINEL`）并注明
    "白名单装模型能说的取值、哨兵是代码兜底"，从代码侧消除这条口径分歧。
- **墙钟断言改组件级**（`tests/test_rumor_agent_offline.py:281`）：原来的
  `elapsed_s < 1.2` 测的是机器闲不闲（报告发现 3/6/9/11）。现在
  `AnalysisState` 记录每个组件的 `spans`，断言改为"最慢组件耗时 < 各组件耗时之和的一半"
  且"各组件起始时间几乎相同"——机器满负载时也不再假红，而真正串行执行仍会失败。

## 九、未修复（明确留给后续）

1. **`agent` 模式的结论仍可能漂移**：证据本来自实时搜索结果，同一文本两次分析的证据集合
   可能不同（报告在"触发条件本身不稳定"里已记录）。缓存只固定了 LLM 组件结果，不固定检索。
2. **分桶步长只挡住已观察到的抖动**：`emotion_score_bucket=2` 让 8.0/9.0 同分，但
   9.0↔10.0 这类边界仍在；要更稳只能加大步长（牺牲分辨率）或提高 `vote_rounds` 类重复调用
   （成倍消耗 API，本轮未启用）。
3. **`credible_stats` 这类"权威统计被某条报道判为反驳"的误抬分**：根因是立场判定把
   "报道同一统计数字但口径略有差异"的一条当成反驳。需要更细的立场判定（比如要求反驳证据
   必须包含明确的否定词或辟谣标记），属检索层问题。
4. **`distill/` 蒸馏链路、本地备选推理**：仍不可用，与本次修复无关。
5. **仓库不是 git 仓库、无远端**：改动只落在本地文件，无法提交/推送。
