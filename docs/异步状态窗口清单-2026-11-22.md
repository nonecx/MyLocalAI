# 异步状态窗口清单（2026-11-22，W1 审计）

**主题**：前端状态翻转窗口 vs 后端异步收尾的系统性排查。
**触发背景**：批次面板"停止竞态"（POST 202 与 SSE 建连之间点停止扑空，提交 53569d5 修复）暴露的同一类问题——**操作已发出但终态未建立/状态尚未翻转**的时间窗内，第二次操作或读取会拿到错误结论。
**审计范围**：`src/mylocalai/web/static/`（chat.js / batch.js / monitor.js / platform.js / profiles.js）与 `src/mylocalai/web/`（batch_api / monitor_api / platform_api / app.py）及直接相关的编排层（tools_monitor / platform.scheduler）。
**口径**：严重度 高=用户可感知错误结果；中=需刷新（或等待）才恢复、或产生重复外发；低=仅日志、短暂不一致或自愈。防护现状分 已防护 / 部分防护 / 无防护。
**约束遵守说明**：本文档只记录与建议、不实施修法；补充的回归测试只追加在 `tests/test_monitor.py`（2 条）与 `tests/test_platform_scheduler.py`（1 条），未改动任何既有用例与生产代码。

## 2. 中高危窗口：复现路径与建议修法（只写方案，不实施）

### #17（高）运行收尾回滚用户暂停 —— tools_monitor._advance 陈旧快照
- **复现**：订阅 enabled=1 → 点「立即运行」（或调度起跑）→ `run_subscription` 持有快照 `sub`（tools_monitor.py:156-159）→ 运行进行中（检索可历时数秒~分钟）用户点「暂停」（monitor.js:397-400，按钮未禁用）→ `PUT /api/subscriptions/{id} {enabled:false}` 落库 enabled=0 → 本轮收尾 `_advance`（tools_monitor.py:112-131）按**快照** `sub.get("enabled")==1` 写回 `enabled=1, paused_reason=""` → 用户刚按下的暂停被静默撤销，订阅按周期继续外发检索。
- **后果**：用户可感知的错误结果（以为已暂停的订阅自行恢复周期运行、持续外发）。
- **建议修法（任选其一）**：
  1. `_advance` 收窄为只写 `last_run_at / next_run_at / last_status`，**不再回写 enabled/paused_reason**（恢复启用本来就只能由用户显式 PUT，与 R8 同向）；"本轮成功后清 paused_reason"改由库内现值判断：收尾前重读 `store.get_subscription`，若 enabled=1 才清 paused_reason。
  2. 保守 CAS：`update_subscription(..., enabled=1)` 改为条件更新 `UPDATE ... WHERE id=? AND enabled=1`（快照值只在为真时参与条件），运行中的暂停不被覆盖。

### #7（中）last_status='running' 残留 → 前端按钮永久禁用
- **复现**：订阅起跑（run-now 或调度）写 `last_status='running'`（monitor_api.py:202 / tools_monitor.py:170）→ 进程在运行中途崩溃/重启 → 库内 last_status 永远停留 'running' → monitor.js:368,389 以 `last_status==='running'` 判定禁用「立即运行」按钮，任何刷新都不会恢复（DB 值不变）；期间列表徽章也停在「进行中」。
- **建议修法**：
  1. 启动回收：web lifespan 起动时对 `last_status='running'` 的订阅写一次孤儿收尾（`last_status='error'`，运行行标 error、注记"服务重启，该轮未完成"），前端按钮即解禁；
  2. 前端兜底：运行中禁用只依据本端 `runningIds`（本端触发的才禁），`last_status==='running'` 仅显示徽章不禁用——点了自然收到后端 409 诚实提示。

### #8 + #19（中）巡检触发 → 首轮状态轮询误判"已结束"
- **复现**：POST /api/platform/scan → `trigger_async`（scheduler.py:87-97）只判断 `locked()` 后即 spawn 线程返回 started=true → 前端 `pollScanDone`（platform.js:928-950）**首个 tick 立即执行**（未先等 SCAN_POLL_MS）→ 后台线程尚未 `_scan_lock.acquire()` → `status().scan_in_progress===false` → 前端立即提示「巡检结束」并 refreshAll——而巡检实际才刚要开始，信息流无新数据。
- **建议修法**：
  1. 后端根治：`trigger_async` 改为"调用线程先同步 `acquire()` 占坑，成功才 spawn 线程并把已持有的锁交给它"（或在 `_run_scan` 外层先占一个进程内 pending 标志），保证返回 started=true 时 `status()` 已能看见占用；`scan_in_progress` 口径改为 `locked() or pending>0`；
  2. 前端兜底：`pollScanDone` 的首个 tick 延后一个 `SCAN_POLL_MS` 再判（首查不作为结束判据）。

### #9 + #18（中）trigger_async check-then-act：双 started、第二条排队
- **复现**：两次快速 POST /api/platform/scan（双击/多标签页）→ 两次都在对方线程持锁前通过 `locked()` 检查 → 都返回 started=true（前端都出「巡检已启动」）→ 第二条线程阻塞在 `_scan_lock` 上，第一条完成后**再跑一轮**（重复外发检索；"不排队不叠加"承诺失效）。scheduler.py:88-91 的注释只覆盖了"误报忙"，未覆盖这一侧。
- **建议修法**：与 #8 同根同修——把"检查 + 占坑"合并成同步原子动作（调用线程先 acquire 成功才受理），第二次调用即得 started=false；不引入排队语义。
- **已锁定部分**：无论该窗口是否触发，两轮扫描**绝不并发重叠**（_scan_lock 串行保证）——本次新增用例 `test_trigger_async_rapid_double_trigger_never_overlaps` 锁定该不变量；既有 `test_trigger_async_single_flight` 锁定忙时拒绝路径。

### #4（中）批次 202 成功但 SSE 建连失败 → 前端谎报"提交失败"
- **复现**：POST /api/batch 返回 202（批次已在后台起跑）→ `consumeStream` 的 GET stream 请求因网络抖动/代理失败非 ok → 抛错进入 catch（batch.js:369-380）→ 显示「提交失败：…」并隐藏进度条；批次在后端照常跑完。用户以为没提交成功，可能重复提交。
- **建议修法**：
  1. 区分两阶段：202 已成功后再失败，提示口径改为"批次已开始运行，进度连接中断；已从列表自动刷新，点开批次可重连"（后端 stream 本就支持直播/重放双路径，重连安全）；
  2. 自动重连：consumeStream 失败后带退避重试 1-2 次，仍失败才落提示并 reload 列表。

### #16（中）monitor 多 worker：_running 集合失效 + 调度线程无闸
- **复现**：`APP_WORKERS>1` 部署 → app.py:72-75 中 `monitor_api.start_scheduler()` **无条件**启动（platform 有 `_WORKERS<=1` 闸、monitor 没有）→ 每个 worker 的调度线程各自 tick，共享同一 DB 的 `due_subscriptions` 会把同一条订阅发给多个 worker；monitor_api.py:38 的 `_running` 是进程内集合，跨进程无效 → 同一订阅多 worker 并发各跑一轮（重复外发、双份证据/运行行）。且 monitor_api.py:14-16 文档声称"多 worker 部署时只有主进程调度"，与代码不符。
- **建议修法**：
  1. 最小改动：lifespan 给 monitor 调度加与 platform 相同的 `if _WORKERS <= 1` 闸，并修正 monitor_api 文档口径；
  2. 若要支持多 worker：把"起跑权"落到 DB（如 `subscription_runs` 插入 running 行时用唯一性约束当租约，插入失败即让行），`_running` 仅作进程内快速路径。

### #20（中）platform 多 worker：POST /scan 绕过 lifespan 的 worker 闸
- **复现**：`APP_WORKERS>1` 时 lifespan 不启动平台调度循环（app.py:74-75），但 `POST /api/platform/scan` → `get_scheduler()`（platform_api.py:61-68）在**任意**收到请求的 worker 里惰性构造 PlatformScheduler 并 spawn 扫描线程 → 不同 worker 的手动触发互相不可见（各自的 `_scan_lock` 独立）→ 跨进程并发扫描 + `/api/platform/status` 各 worker 自报状态。
- **建议修法**：多 worker 模式下 `/scan` 直接 409（说明单 worker 前提）；或把单飞状态落 DB（`scan_runs` 存在 status='running' 行即拒绝新触发，以库为准）。

## 3. 已修案例（作为同类窗口的修复范式引用）

### 范式一：批次停止竞态（提交 53569d5）
- **窗口**：POST /api/batch 返回 202 之后、SSE（GET /stream）真正建连之前，前端没有可断的流——此刻点「停止」扑空，批次在后端继续跑完，前端却显示已停止。
- **修法（前端意图闩 + 后端取消链配合）**：
  - 前端记录停止**意图**（`state.stopRequested`，batch.js:96-97）而非立即动作；`consumeStream` 建连成功后的第一件事就是检查该闩，命中即立刻 abort（batch.js:420-427）——把"没有流可断"转化为"一连上就断"；
  - 后端断开即取消原语早已就位：`_live` 的 finally `events.request_cancel()`（batch_api.py:330-339），run_batch 经 `cancel_check` 轮询协作收尾（batch_api.py:204-209）；
  - 配套：停止后延迟 2.5s 刷列表（batch.js:398-403），避免徽章停在「进行中」。
- **测试锁定**：后端取消链 `tests/test_batch.py::test_stream_disconnect_cancels_running_batch`（:638）；前端闩暂无 JS 级测试（本仓库前端契约走静态断言，不在本次允许追加的文件范围）。
- **范式要点**：**把不可操作的空窗变成"登记意图、就绪即执行"**；终态永远以后端落库为准，前端提示只描述本地发生了什么。

### 范式二：run-now 起跑竞态（提交 e72865a，R2/R8/R9 同批）
- **窗口**：run-now 202 返回后、后台线程写出终态之前，订阅行的 `last_status` 还是**上一轮**的终态——前端首轮轮询会把旧终态误读为"本轮已完成"（假完成）。
- **修法（起跑即占状态）**：
  - 请求线程在 202 前同步预建运行行（`start_run`，响应体带 `run_id`）并 `mark_running`（monitor_api.py:201-202）——状态翻转发生在返回之前，轮询首轮必见「进行中」；
  - 前端完成判据优先按响应里的 `run_id` 核对**该轮运行行**终态，取不到才回退 last_status（monitor.js:601-606 注释口径）；
  - 调度路径同口径：`run_subscription` 内 `store.mark_running`（tools_monitor.py:170）。
- **测试锁定**：`tests/test_monitor.py::test_run_now_marks_running_then_terminal`（:429，用阻塞 stub 拉长中间态）。
- **范式要点**：**202 响应体携带本轮身份标识（run_id/batch_id），前端按"本轮行"判终态，不用会被下一轮覆盖的聚合字段**。
