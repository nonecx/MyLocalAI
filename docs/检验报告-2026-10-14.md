## 1. 结论摘要

- **程序稳不稳：基本能用，但有两条真实的不稳定。**
  同一段文本重复分析，四档结论会在「疑似情绪化谣言」和「高度疑似水军/煽动性言论」之间跳
  （`.tmp/verify/out/determinism.json` 的 rumor，`unstable_fields=[emotion_score, aggression, conclusion]`）。
  根因是上游大模型在 temperature=0 下仍有采样漂移，而下游判据没有护栏：
  classic 模式（网站默认）的结论翻转由 `aggression` 字段在「中/高」间抖动驱动（首条规则 `core_judge.py:69` 要求 `aggression=="高"`）；
  另有第二条独立路径——agent 模式把 `emotion_score` 的 1 分抖动放大成 2 分，`verdict.py:120` 正好跨过 45 分阈值。
  两条都真实存在。**不是测量噪声**：复核员的顺序（无并发）对照实验里，同一文本连调 6 次 `analyze_aggression` 得「中/高」＝5/1、`emotion_score` 稳定在 9.0，
  即不用并发也会漂移（该对照实验由复核环节完成，输出记录在复核笔记中，**不在 `.tmp/verify/out/` 落盘**）。
  另有一条"离线回归测试"闸门为红，但根因是测试自己写了绝对墙钟阈值（`tests/test_rumor_agent_offline.py:281`），
  机器一忙就误报，不是产品串行缺陷。
- **扛不扛压：4 并发不降级，但缺请求级保护。**
  模块级与全链路级各跑 1/2/4 并发：0 异常、0 限流、0 报告回退。
  全链路 p50 相对并发 1 的倍数依次为 `[1.0, 2.17, 1.06]`（三个数分别对应并发 1、2、4；对照组是并发 1）。
  注意并发 2 时 p50 已达 2.17 倍——闸门这里判"不降级"的口径是**只看有无异常/限流/降级**，
  **不是**看延迟倍数（`.tmp/verify/harness.py:1073` 只要求 `errs==0 and not limited`），所以"不降级"不意味着并发下延迟不涨。
  网站并发 4 打 `/api/analyze` 成功率 1.0（`.tmp/verify/out/digest_final.json`）。
  但整条链路只有一条同步大模型通道，上游不可达时单次 `/api/analyze` 最差耗时可达 515.8 秒且不可中断，
  会占满线程池（详见发现 7）。**重点：这是本机 127.0.0.1 单用户演示服务，影响面限于本机。**
  依据：`my_website/start.bat:18` 用 `--host 127.0.0.1` 且无 `--workers`（单进程）；`my_website/app.py` 全文件 grep 不到 auth/token/login/Depends 等鉴权（`grep -rniE "auth|bearer|password|login|api[_-]?key|Depends\(|OAuth" my_website/app.py` 无命中，退出码 1）；
  历史记录是进程内全局变量 `_history`（`app.py:69`）、无用户/会话概念。**这三条只证明"单进程 + 无鉴权 + 无用户区分"，"仅本机"由监听地址推出；"单用户"无代码级证据，是演示部署的合理推断，非实测。**
- **功能有没有落地：核心功能都在，且有防退化保护。**
  空输入短路、报告回退、四档裁判规则网格 128/128、两种言论分层实现 200/200 等价、无事实声明封顶 24、
  可靠辟谣抬到 78 分、边界/对抗输入不崩溃、CLI 与 MCP 4 个工具对外契约、谣言 Agent 端到端 7/7 命中——
  都已实测通过。**但有 4 项闸门未通过，其中 2 项是校验器判据写错造成的假阴性，2 项是真实问题。**

一句话：**功能落地情况良好，抗压到 4 并发没问题；真正的短板是"同输入结论会漂移"，以及判定口径全部写死在代码里、换行业/换语境要改 Python。**

### 术语速查（先看这里，后文都用这些词）

- **三档运行模式**（用户提问里的"mode"，`my_website/app.py:44` 的 `VALID_MODES`）：
  - **classic（经典模式，网站默认）**：`core_judge.judge` 串行调用情感/攻击性/逻辑三个分析模块，规则引擎给一个**结论**，`report_generator` 生成报告。这是默认路径。
  - **agent（智能体模式）**：`RumorAgent` 调度多个工具（含联网搜索证据），输出**标签 + 0-100 风险分**。耗时更长（约 30-120 秒）。
  - **pipeline（降级模式）**：不是用户可选，是 agent 内部在模型不可用/网络故障/超时时**自动退回**的本地规则管线（`.tmp/verify/out/digest_final.json` 的 `agent_fault.modes=["pipeline"]`）。
- **四档结论**：规则裁判把文本判成四类之一，名称与出现处：`高度疑似水军/煽动性言论`、`疑似情绪化谣言`、`理性探讨`、`情绪化宣泄/普通网络争论`（定义在 `core_judge.py:69-75` 的 if-else）。
  - 注意区分两套"档"：上面这套是 **classic 的结论**；agent 模式另有五个**风险标签**：`高风险谣言`、`疑似谣言`、`存疑待核实`、`低风险`、`无可核实陈述`（`verdict.py:20-24`），以及一个**言论分层的档名** `高度疑似水军/煽动性言论`（`verdict.py:54`，与 classic 首档同名同规则）。
  - 闸门里的"四档裁判规则网格 128/128"指前一套（classic 四档）；"言论分层两处实现等价 200/200"指 `verdict.speech_tier` 与 `core_judge` 那套逐条对齐。
- **证据本（evidence book）**：agent 模式联网搜索后整理出的证据清单，每条含来源 URL、`domain_tier`（5 级信源分级）、立场（支持/反驳/无关）等，是网站证据区展示的数据结构（字段见 `rumor_agent/agent.py:174-180`）。**"证据本"是项目自有名词，不是笔误。**
- **原始数据能否获取/重跑**：`.tmp/verify/` 与 `.tmp/verify/out/*.json` 是本地采集目录；**本仓库不是 git 仓库**（`.tmp/verify/out/static.json` 的 `has_git_repo=false`，根目录也无 `.git`），所以这些原始数据**未入库、不能靠 clone 获得**。脚本可重跑，命令在 `.tmp/verify/harness.py:8-18` 顶部注释里（如 `.venv/Scripts/python.exe .tmp/verify/harness.py determinism --repeat 5`）。
- **关于"已独立复核"的执行者**：本报告由我（报告撰写人）撰写；第 4 节标注的"已独立复核"是**另一名复核员**对我此前初判发现的核查，复核方法与结论都写在各条下方。**复核结论按原样保留，即使与我初判不一致也照实写出**（多处严重度被复核下调）。我本人未再重跑那批复核实验。

### 组件数说明（后文出现的 4/5/6 个组件）

生产代码里一个分析请求共 **6** 个组件，定义在 `rumor_agent/state.py:18`：`("markers", "emotion", "aggression", "logic", "claims", "evidence")`。其中 `markers` 是纯本地正则扫词（`scan_markers`，不耗时也不联网）；`emotion`/`aggression`/`logic` 走 LLM（`language_module`/`logic_module` 里的 `chat_json`），`claims` 走 LLM（`extract_claims`），`evidence` 联网（`_collect_evidence`）。测试 `test_rumor_agent_offline.py:271` 给其中的 **5** 个（emotion/aggression/logic/claims/evidence）各注入 0.3s 延迟，但断言文案（`:281`）写的却是"四个 0.3s 的组件"——**这是测试文案本身少数了一个**，不是报告里数字打架。后文凡提到"组件数"都按此口径：production=6、被测延迟桩=5、断言文案=4。

### 发现 1（泛用性）判定口径写死在代码里，换行业/换标准必须改 Python

- **位置**：`rumor_agent/verdict.py:28-31`、`rumor_agent/verdict.py:144-147`、`rumor_agent/sources.py:41-60`。
- **是什么**：风险分阈值、无事实声明封顶、证据抬分锚点全是源码字面量；信源分级名单也是硬编码域名表，没有外部配置入口。换语境只能改代码，改提示词没用。
- **证据**：`verdict.py:28-31` 有 `NO_CLAIM_RISK_CAP = 24 / THRESHOLD_HIGH = 70 / THRESHOLD_SUSPECT = 45 / THRESHOLD_DOUBT = 25`；`verdict.py:144-147` 有 `evidence_pts = max(0, 78 - risk)` 与 `max(0, 58 - risk)`（我逐行读了确认）；`sources.py:41-60` 的 `_register(...)` 把域名→等级写进 `_DOMAIN_TIERS`。全仓 grep `json.load(open|yaml.safe_load|tomllib|configparser|BaseSettings` 返回空。
- **严重度**：初判 high，**复核修正为 medium**。
- **已独立复核**：是。复核方法：读 `verdict.py`/`sources.py` 全文 + AST 确认常量为 int 字面量 + 跑 `classify_domain`/`source_kind` 实测 + 三条 grep。复核结论：**主体成立，但原措辞"把官方名单硬编码成中国域名"不准确**——官方档还含 `who.int`、`cdc.gov`，媒体档含 `reuters.com`、`bbc.com`、`apnews.com`；实测这三个英文源都判为"权威媒体/辟谣平台"，只有 `bbc.co.uk`、`nytimes.com` 等未收录域名降为"未知来源"。所以这是**覆盖不全**，不是"换英文语境就整体失效"。且 `sources.py:12-13` 明确写了名单不完整、"宁可低估"是有意取向，属已记录的设计取舍，故降为 medium。

### 发现 2（泛用性）只配一个模型提供方，且更换供应商存在静默错配

- **位置**：`shared_core/llm_client.py:29-30,47-52,55-62`；`rumor_agent/llm.py:11-38`；`requirements.txt:26-31`。
- **是什么**：换模型要同时改 base_url、model、key 三个变量；只改密钥会继续把请求发往 LongCat 代理。
- **证据**：`llm_client.py:29-30` 内置 `_DEFAULT_BASE_URL="https://api.longcat.chat/openai/v1"`、`_DEFAULT_MODEL="LongCat-2.5-Preview"`（我读了确认）；`:47-52` 密钥按 LONGCAT→DEEPSEEK→OPENAI 取值，但 `:55-62` 的 base_url/model 只认 `LONGCAT_BASE_URL`/`LONGCAT_MODEL`。初判实测：清空 `LONGCAT_*` 只设 `OPENAI_API_KEY=sk-fake-openai`，客户端仍建到 LongCat 地址。全链路无 fallback（grep 无命中）。`requirements.txt` 的 torch/transformers/modelscope 在"可选"注释块外，会被 pip 一起装。

### 发现 7（抗压性）全服务只有一条同步大模型链路，单次 `/api/analyze` 最差 515.8 秒且无请求级超时预算

- **已独立复核**：是。复核方法：读断言与 `agent.py`/`state.py` + 空载/负载实跑 + 读 `unit.json` + `-X importtime` 检查导入时机。复核结论：**结论成立，根因描述有一处不准确**：原发现把"该进程首次导入 langchain/langgraph 与 Agent 构造"列为失败原因——这对**单独跑该用例**成立（导入约 0.22s 落在计时窗口内），但对**整包 158 测试**不成立：同类的 `test_agent_skipping_tools_is_backfilled` 按字母序排在最前，早已把 langchain 导入预热，等本用例运行时导入已 warm，其 2.3s 完全来自负载下的线程调度延迟。另：断言阈值 1.2s 本身对并行度是**有效**的（并行≈0.3–0.5s，串行≥1.2s），问题准确说是"墙钟阈值断言在负载下不稳"，而非"阈值选错"。

## 5. 优化方案

### 【泛用性】

1. **把判定口径抽成外部配置。** 改什么：把 `verdict.py:28-31` 的 4 个阈值、`:144-147` 的 78/58 锚点、`sources.py:41-60` 的信源分级表挪到一个可读的配置文件（JSON/YAML 或 `pydantic-settings`），代码只读不写死。
   - 为什么：现在换行业/换判定标准只能改 Python，配置面只有 `.env` 一个。
   - 怎么验收：新增一个配置加载测试，改配置值后 `assess()` 的门档随之变化；全仓 grep 不到裸阈值字面量。
2. **信源分级名单外置并补全。** 改什么：域名→等级表外置成数据文件，补上 `bbc.co.uk`、`nytimes.com` 等主流英文源；`sources.py` 文档与实现统一（"其他" vs "非官方"二选一）。
   - 为什么：当前是覆盖不全 + 文档自相矛盾；名单外权威会被降为"未知来源"，证据抬分失效。
   - 怎么验收：对一份含中英主流源的固定清单跑分级，断言"可靠/不可靠"分类符合预期；文档描述与返回值一致。
3. **多提供方配置 + 启动自检。** 改什么：让 base_url/model/key 三者成组绑定（如 `PROVIDER=longcat` 一键切换），启动时校验密钥与服务商是否匹配，不匹配直接报错而不是静默发请求；把 `requirements.txt` 里的 torch/transformers/modelscope 挪进可选注释块或独立 `requirements-optional.txt`。
   - 为什么：现在只改密钥会继续发往 LongCat，401/超时看不出是配置错；pip 会连带装数 GB 本地推理栈。
   - 怎么验收：只设 `OPENAI_API_KEY` 时启动即报"密钥与服务商不匹配"；`pip install -r requirements.txt` 不再安装 torch。
4. **去掉写死的 `D:/MyLocalAI`。** 改什么：`tests/run_module_tests.py:34-36`、`smoke_api.py:5`、`smoke_local.py:7`、`verify_fixes.py:6` 及 README/app.js 里的绝对路径改用 `Path(__file__).resolve().parent.parent` 或相对路径。
   - 为什么：运行期受影响的是 `run_module_tests.py`（写到固定目录），其余是文档/冗余路径；总之不该依赖固定盘符。
   - 怎么验收：把仓库复制到另一盘符/另一用户名下，四套件仍能跑通。

### 【稳定性】

5. **给结论加滞回/去抖，不让 1 分抖动翻档。** 改什么：`verdict.py:120` 的 `emotion_pts=round(score*2)` 改为区间取整（如按 0.5 分粒度），风险分跨阈值时引入小滞回带；对 `aggression` 这类决定首条规则的字段做一致化（如连续两次一致才采信，或对该字段取更粗的分档）。
   - 为什么：8.0→46 与 7.0→44 正好跨 `THRESHOLD_SUSPECT=45`，1 分抖动就翻档，用户看到不同结论。
   - 怎么验收：对固定文本重复调 20 次，四档结论与得分完全一致（把"同输入结论可复现"闸门从红变绿）。
6. **调用时传 `seed` 并收敛采样参数。** 改什么：`shared_core/llm_client.py:133-137` 补 `seed` 参数；如供应商不支持，则在上层对关键字段做多数表决/缓存复用。
   - 为什么：temp=0 仍漂移是上游行为，需在工程侧加护栏。
   - 怎么验收：同一文本重复调用，关键字段（aggression/emotion_score/fallacy）不再出现多值。
7. **修两条假阴性判据。** 改什么：`harness.py:991-992` 的信源判据改为断言"伪装域名**不被判为官方**"（而非 `startswith("非官方")`）；`harness.py:248` 的枚举判据把哨兵值"未知"排除在"必须 ∈ 枚举"之外，或改为断言"回退到默认值"。
   - 为什么：这两条会把正确行为判红，可能误导改坏反伪装逻辑。
   - 怎么验收：修完后"枚举白名单回退""信源分级抗伪装"两项闸门转绿，且被测代码不变。
8. **把墙钟计时断言改成组件级计时。** 改什么：`tests/test_rumor_agent_offline.py:281` 不再断言 `analyze()` 端到端墙钟 `<1.2s`，改为断言各组件 `component_timings` 的**并发重叠**（如各组件起始时间差在容差内），或对端到端阈值给足 5–10 倍余量并允许重试。
   - 为什么：现在它测的是机器闲不闲，会在忙碌时持续假红、掩盖真回归。
   - 怎么验收：加 24 个 CPU 忙进程时该用例仍稳定通过；真正串行执行时能稳定失败。

### 【抗压性】

9. **加请求级超时预算与排队上限。** 改什么：`my_website/app.py` 的同步端点在应用层加统一 deadline（如整请求 ≤ 120s）、对 `/api/analyze` 加显式并发上限/排队，并给前端 `app.js:179` 的 `fetch` 加 `AbortController` 允许用户取消。
   - 为什么：上游不可达时单次最差 515.8s 且不可中断，会占满线程池拖住 health/history。
   - 怎么验收：把 `LONGCAT_BASE_URL` 指向不可达地址，`/api/analyze` 在预算内返回降级结果；期间 `/api/health` 仍可响应；前端可中断。
10. **失败快速返回，缩短放大。** 改什么：`llm_client.py` 缩短单次超时/重试次数，或对同一请求内的重复调用（`extra_body` 回退导致每次翻倍）做短路。
    - 为什么：单模块 6 次 HTTP 串行放大到约 130s（若遇静默丢包地址最坏可近 360s），是超长耗时的直接来源。
    - 怎么验收：不可达地址下单模块耗时降到目标预算内。
11. **让超时线程真正停下。** 改什么：`agent.py:150-159` 改为可协作取消（在工具/LLM 调用内检查取消标志），或至少把后台线程设 `daemon=True` 并限制其继续发起联网/LLM。
    - 为什么：`cancel_futures` 不打断运行中 future，超时返回后后台仍在跑。
    - 怎么验收：超时返回后 `+3s` 组件调用计数不再增长；短命 CLI 进程能按时退出。

### 【功能性】

12. **前端展示口径与 README 对齐。** 改什么：`app.js:331` 除了 `domain_tier` 也展示 `source_kind`（官方/非官方），或在 README 里把口径改成实际展示的 5 级 tier；二选一，别再两套。
    - 为什么：文档承诺两分，页面显示 5 级，用户看不到"官方/非官方"这个关键信号。
    - 怎么验收：网站证据区同时可见两分口径（官方/非官方）；README 描述与页面一致。
13. **把 `sources.py` 文档与实现统一。** 改什么：确定名单外域名的契约值（"其他"还是"非官方"），同步 `sources.py:89-92` 的文档字符串与 `:97,111` 的返回值。
    - 为什么：文档说"其余一律归非官方"、实现返回"其他"，两者矛盾。
    - 怎么验收：文档描述与 `tests/test_rumor_agent_offline.py:493` 锁定的契约一致。
14. **补 README 与 `.env.example`。** 改什么：仓库根补 `README`、`.env.example`，说明必需的密钥/模型变量与启动步骤。
    - 为什么：当前根目录无 README、无 `.env.example`，新人不知道要配哪些变量。
    - 怎么验收：照 `.env.example` 配好即可启动；README 步骤可复现。

## 6. 未覆盖与已知局限

- **本次报告未重跑全部 25 项闸门。** 其中真实 API 类闸门（复现性、并发、Agent 端到端、边界输入、网站压力）需要联网重跑并消耗大量 API 调用，成本很高。本报告的闸门结论**引用作者自采的 `.tmp/verify/out/` 原始数据**；只有部分发现另有独立复核（第 4 节逐条标注了复核方法）。凡"引用"而非"我跑"的，都不算我这边通过。
- **假阳性/假阴性风险**：第 3 节 4 项未通过里，2 项（枚举白名单回退、信源分级抗伪装）已被复核判定为**校验器判据写错**，不是产品缺陷——现闸门仍显示"未通过"，是闸门自身要修。
- **未验证的具体数字**：发现 3 的"连续 11 次全套件全 OK"、发现 8 的线程数与 calls 计数——**复核员未能复现，且原始数据中查无记录**，这些数字不可作为可靠证据引用。发现 4/10 的漂移分布（2/5 vs 4/5）逐次随机，也不应当作固定值。
- **负载敏感性无法给出稳定阈值**：发现 6/9/11 的计时断言，复现所需的 CPU 忙进程数随机器核数与负载而变（复核员需 24 进程才稳定复现），**这是量级差异，不影响"该断言负载敏感"的结论**。
- **影响面限定**：抗压性问题（发现 7、8）都基于本机 127.0.0.1 单进程、无鉴权演示服务的部署形态（依据见结论摘要：`start.bat:18` 监听 `127.0.0.1` 且单进程，`app.py` 无鉴权代码，`_history` 为进程内全局变量）；换成多用户公网部署，后果会更严重，但**本项目当前不是那种部署**。"单用户"无代码级证据，是从"本机 + 无鉴权 + 演示形态"作出的推断，非实测。
- **未测项**：未做长时间稳定性浸泡测试（连续运行数小时）、未做真实恶意 URL/SSRF 攻击面测试、未验证浏览器端各主流浏览器兼容性、未评估真实模型供应商的限流配额策略——这些不在本次 25 项闸门范围内，风险大小未知（未验证，不作估计）。
