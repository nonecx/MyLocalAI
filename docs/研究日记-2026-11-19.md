## 0. 一句话

这个项目最初的命题是「哪些发言像水军」，最后的命题变成了「**帮人减轻处理信息的压力**」。
中间隔着一台在卡死与黑屏之间轮换的电脑、一次被迫放弃的本地训练、一次推倒重来的架构重塑，
以及二十天里把「能跑」改造成「可演进」的工程账。

---

## 1. 起点：评论区里的那些话（口述）

真正的起点不是技术，是阅读体验。

看视频、看新闻的时候，翻到下面的讨论区：大量评论不关心事实是什么，只在意贬低、宣泄、攻击别人，
而这些情绪化的表达又会误导后面进来的人。网暴事件频发的新闻看多了，就想试着写个程序。

最初的想法非常具体：**做一个简单的应用，从逻辑、语言、攻击对象三个角度分析一段文本，
指出哪些发言大概率是水军制造的。**

这里有一个后来一直保留的方法论：先观察现象、再归纳特征、最后才写代码。
三个维度不是从论文里抄的，是从「水军怎么说话」这件事里拆出来的：

| 维度 | 观察到的现象 | 想要的输出 |
| --- | --- | --- |
| 情感 | 煽动为主，强度高、正负无关（狂热和愤怒一样是高分） | 情感倾向 + 情绪化强度 0–10 + 关键词 |
| 攻击性 | 不针对论点，针对人/群体，或者制造对立 | 攻击对象 + 攻击等级（高中低）+ 攻击类型 |
| 逻辑 | 论据与结论之间没有真实支撑，靠情绪和立场连着 | 论据 / 结论 / 逻辑关联性（强中弱）/ 谬误类型 |

## 2. 第一版：三个模块 + 本地微调（复核）

第一版的产物今天还在：`F:\kc\MyLocalAI`（文件时间集中在 2026-09-22 → 09-27）。
这是一个**本地训练 + 规则裁定**的架构，技术路线写得很明确：

- 基座：`Qwen/Qwen2.5-0.5B-Instruct`，LoRA 超参 `r=8, alpha=32, target_modules="all-linear"`；
- 三个模块各自一份数据、一份训练脚本、一份 adapter 权重（`module_emotion/`、`module_attack/`、`module_logic/`）；
- 调度器 `core_judge.py` 做了一件很朴素但必要的事：**逻辑上并发、物理上串行**——
  `ThreadPoolExecutor(max_workers=1)`，每个模块推理前挂载自己的 LoRA、推理后 `delete_adapter` + `torch.cuda.empty_cache()`，
  保证同一时刻显存里最多只挂一个 adapter；
- 三个模块跑完，用 `RuleEngine` 的 if-else 出四档结论（高度疑似水军/煽动性言论 → 疑似情绪化谣言 → 理性探讨 → 情绪化宣泄/普通网络争论）；
- 最后由 `report_generator.py` 按固定模板（含 emoji、免责声明）渲染成一段中文报告。

站在今天回看，这个设计的三条判断其实都对：**任务拆得动、指标可枚举、裁定不交给模型**。
错的是执行载体——它假设「我能在自己的电脑上把模型训出来」。

## 3. 撞墙：那台一直卡死和黑屏的电脑（口述）

训练阶段留下的记忆很直接：**电脑在卡死和黑屏之间轮换**。

不是一次失败，是反复失败。0.5B 的模型、三份 LoRA、本地显存档位、依赖版本、checkpoint 恢复……
每一件单看都不算大，叠在一起就是「跑一次要赌一次，赌输一次要重来」。
有几次训练脚本里甚至写了按验证集准确率决定「是否回退、重启、继续推」的重启逻辑，
那是被中断逼出来的写法，不是设计出来的写法。

结论来得很快：**本地小模型根本训不起来**。原因不神秘——没钱、没时间，
而且以当时的条件，硬磕训练的风险收益比是负的：训练要的是稳定算力和长时间占机，
而这两样恰恰是最缺的。

于是做了转向：**不做训练，做 Agent。**把「模型要学什么」换成「模型要调什么」。

## 4. 第一次 Agent：效果不好（口述）

转向 Agent 之后，第一版效果并不好。

但不好在哪，值得写清楚：那三个突破口**被完整保留下来了**，
它们从「每个模块一份 LoRA」变成了「每次分析里的三个确定性信号」——
今天翻开代码仍然能看到这条线的连续性（复核）：

- `src/mylocalai/core/tiering.py`：分层裁定仍然是「情绪强度 + 攻击等级 + 逻辑关联性」三元组；
- `src/mylocalai/classic/language.py` / `src/mylocalai/classic/logic.py`：提示词、枚举白名单、默认值一路继承；
- `src/mylocalai/rumor/tools.py`：给 Agent 挂上 `analyze_emotion` / `analyze_aggression` / `analyze_logic` 三个工具；
- `src/mylocalai/rumor/verdict.py`：仍然只用这些确定性信号算分，模型不参与打分。

也就是说，那一次转向没有丢掉内核，丢掉的是「我自己训练模型」这个前提。
后面所有扩展（联网取证、证据本、关注度、深读、档案库、对话助手），都是从这三个突破口**长出来的枝**，
而不是换了另一棵树。

至于「最初效果不好」的判断依据，作者的说法是「**从它的发言就能感受出来**」——
这句话放在今天依然成立：判断一个核查类系统行不行，先看它敢不敢说「我不知道」，而不是看它的分数多漂亮。

## 5. 认知转折：人们要的不是「识别水军」（口述）

真正改变项目形态的，不是技术升级，是一次对需求的重新判断：

> 在后来的调研和项目体验里我发现，人们更需要的不是「识别水军言论」，
> 而是**帮忙分担信息处理压力**。

这两件事看着相近，工程含义完全不同。

「识别水军」是一个**判断发言者**的任务：给一段话打上「像水军」的标签，输出一个结论就结束了。
「分担信息处理压力」是一个**替用户消化信息**的任务：用户丢进来一条说法，
要拿回去的是「当前证据支持什么、还缺什么、什么时候值得再看」，
以及一张能在十秒内读完的卡片。

这次转折让后面所有取舍都有了裁判标准（复核，见 [工作指导-智能助手重塑-2026-10-30.md](工作指导-智能助手重塑-2026-10-30.md)）：

- 回应默认要短：先一句话结论，再一张卡；
- 卡片分三层：标签 + 置信度 → 证据计数 / as_of / 降级徽章 → 展开看证据；
- 深挖按需：六章节档案是助手的**工作记忆**，不是用户必须面对的产品面；
- 慢查不允许白屏：先给零成本本地初扫，再给组件级进度；
- 降级也要体面：断网、上游挂掉时如实说「没查到」，不编。

作者对此的补充很克制：这些想法不是一次想通的，**都是在体验中不断更新的**。
不是先有完美定位再动工，而是边做边被体验修正。

几个当时想清楚的设计决定，值得单独记一笔：

**① 依赖方向只有一条线。**`core ← llm ← retrieval ← {classic, rumor, attention} ← {dossier, assistant} ← web/cli/mcp`，
且 classic / rumor / attention 三者互不 import。这条线不是靠约定，是用 AST 静态测试锁的——
Python 项目里，「谁都能 import 谁」是腐化最快的地方。

**② 卡片永远在叙述之前。**结构化结果先落事件流，叙述只是解释。叙述模型挂了，卡片照发。
这条在 M4 之后被反复验证是对的：LongCat 有返回空 content 的前科，而结论不能跟着上游一起丢。

**③ 大模型不参与打分。**标签、风险分、置信度、E 分全部由纯函数从证据本/信号推导。
这条从第一版的 `RuleEngine` 一路守到今天，也是这个项目最经得起追问的一点。

**④ 数字由测试守。**README 里写的用例数不再是手工维护的字符串，
而是 `tests/test_readme_counts.py` 去核对——文档漂移这件事，被当成缺陷处理。

## 7. 十一月：从「功能」到「合同」（复核）

11 月的重心从「还能加什么」转向「怎么说清楚、怎么管住」。两个大动作：

**（1）用户能力 Skill 化。**能力被收敛成四个：
`claim-checking`（事实核查）、`evidence-research`（证据研究）、
`topic-understanding`（话题理解）、`speech-understanding`（言论理解）。
每个能力在 `capabilities.json` 里带三样东西：能触发它的动作、**硬门禁**（`narration_policy`）、
以及合法结果清单。落地的三层是（复核）：

- 路由层：选工具之外，额外判定「这次请求属于哪个用户能力」，非法值回落确定性映射；
- 叙述层：按能力把 `narration_policy` 拼进 system prompt，`narrate_system` 本体一字不改
  （`src/mylocalai/assistant/loop.py`，空能力时 system 与旧版逐位一致）；
- 结果层：`boundary_check` 做统一边界检查（`src/mylocalai/assistant/capabilities/catalog.py`），
  比如「证据研究不得建档」「证据研究不得输出结论卡」是写进策略、由测试锁定的硬违规。

**（2）取证三技能。**`identify-domain → discover-sources → retrieve-evidence`，
一条只读取证流水线（`src/mylocalai/assistant/skills/`）。它的分工很干净：
`SKILL.md` 管判断口径、JSON 管名单与预算、Python 管约束与检查。
几条只靠代码保证的事：信源身份不能自封（陌生域名最多 `unverified_candidate`）、
引文必须逐字出现在已抓取正文里并记录字符偏移、逐跳重定向复核 + DNS 钉扎、
`site:` 由代码拼接（模型给的会被剥掉）。

**（3）隐私门禁 fail-closed。**`src/mylocalai/core/privacy.py`：默认 `external_processing_enabled=false`、
provider 名单为空、三类保存开关默认关闭；非 loopback 地址必须总开关开启且 provider 在名单里才放行，
否则抛 `PrivacyAuthorizationError`；配置损坏回落默认并告警。
「激活自动授权」只是在总开关已开时省掉重复授权的手续，**不绕过开关、不自动开总开关**。

作者对 11 月这条线的定性很清楚：**规格的方向是收紧模型的自由度，不是扩大自主性**。
路由只输出封闭结构（能力 id / 意图 / 输入 / 澄清），执行图由代码按已登记的能力与组合模板展开，
模型不得提交任意工具步骤列表、不得增删必经步骤；「是否深读」属于能力内部受控流程与合法业务出口
（`not_triggered` / `not_applicable` 必须如实说明），不是模型可以自由加戏的空间。
这套东西的下一步蓝图是 [Agent工作流规格-v0.1.md](Agent工作流规格-v0.1.md)——
比赛期间冻结，不动。

## 8. 现在进行时：赛前三天（复核 + 口述）

此刻的状态是「比赛演示就绪」。演示方案见 [比赛演示方案-2026-11-17.md](比赛演示方案-2026-11-17.md)，
核心是**双轨**：有网走联网轨（四能力全流程），没网走离线轨（确定性四档、诚实降级、指纹秒回、手动算分、档案与参谋）。

风险排序（作者判断，已按实际发生情况排）：

| 排序 | 风险 | 是否真实发生 | 缓解是否已在演示分支 | 观众会看到什么 |
| --- | --- | --- | --- | --- |
| 1 | 网关「建连后不给响应」 | **是**（11-18 实测） | 部分 | 「卡死」，像程序坏了 |
| 2 | 现场断网 | 否 | 部分（离线轨） | 能力缩水但仍自洽 |
| 3 | 评委临时输入一条说法 | 否 | 是（设计内） | 慢、证据薄，不翻车 |

**为什么最怕第一种。**这不是假想：TCP 建连成功、HTTP 层永不回包，线程卡在 socket 读上。
轮预算（`turn_deadline_s=180`）是协作式检查——只在开工前、两次尝试之间看一眼，
压不住一次被吊死的读。实测表现是：服务进程 80+ 秒 CPU 零增长、请求数恒为 0、**没有任何 SSE 事件**，
前端永远停在骨架屏，只能手动重启。观众看到的就是「项目卡死」。

已经落地的缓解（三层，都是兜底不是替代）：
路由段独立预算 40s（`route_deadline_s` / `CHAT_ROUTE_DEADLINE_S`，超时以 `error{code:"routing_timeout"}` 收口）、
回合看门狗（轮预算 + 15s 宽限，代发 `error{turn_watchdog}` + `done`）、
前端 15 秒无事件追加「等待中」提示、预算紧时禁用客户端内部重试防止 40s 被悄悄翻倍。

**残余风险才是「现在」的担心点**（复核，截至本日记写作时）：

- 路由预算那一刀在 `fix/route-phase-deadline`（`266e955`），演示文档所在分支 `fix/competition-demo-readiness` 没有它；
- 看门狗只能 `abandon()` 丢弃迟到事件，**杀不掉被挂住的 daemon 线程**，最坏仍是每回合等 40s 才报错；
- 11-18 全量 CI（1390 例）有 5 例红，且都在路由缝上（路由失败语义从 `clarify` 改成 `system_error` 之后测试没跟上）；
  已用基线 worktree 复现，确认是存量问题、非新回归，但「CI 全绿」这句话赛前不能讲。

**断网为什么只排第二。**确定性的部分是真实确定的：档案、指纹、参谋、导出、手动 E 分全在本地 SQLite，
classic 四档是纯函数。但有一个代码事实——**对话入口的路由本身也是一次 LLM 调用**。
冷启动 + 全断网时，`route_llm` 抛异常 → `system_error` → 回通用文案，
没有确定性关键词兜底；而 LLM 缓存是进程内、TTL 900s、不落盘，
所以「同文本秒回」只在同进程 + 同 prompt + 15 分钟内成立。
结论：离线轨走工具 Tab（`/api/analyze`）可行——那条路不经过助手路由；走对话入口，冷启动全断网会直接失败。
演示方案 §2.2 没写死每条脚本用哪个入口，这是执行风险。

**至于「离线轨是否完整实测过」**，作者给的答案比文档诚实：
文档声称 2026-11-17 20:39–21:05 断网实测过、并给了单条耗时（如 85.5s）；
但仓库里同时段能查到的只有一份启动日志，离线套件日志是 10-30 的 624 例子集；
11-18 的看门狗、路由预算、`abandon()`、前端改动都发生在这次「实测」之后，没有断网重跑。
所以准确说法是：**能力级验过、数据预埋是真的；端到端「冷启动 + 全断网 + 按脚本走」没有可复现证据。**

赛前 24 小时的补测清单（作者自拟，原文保留）：

1. 真飞行模式 + 冷启动进程，按 §2.2 逐条走一遍，记录每条耗时与 SSE 事件序列；
2. 脚本写死入口（每条动作标明「工具 Tab」还是「对话」）；对话入口的指纹秒回改成「先在线预热同文本 → 再断网」，
   确认进程不重启、不超 15 分钟 TTL；
3. 补合分支、打 tag：把 `266e955` 合入 `fix/competition-demo-readiness`，打 `competition-demo` tag；
4. `.env` 快切做成脚本（离线两行 `LLM_TIMEOUT_S=8` / `LLM_MAX_RETRIES=0` 一键加、一键回切，各验一次）；
5. 保留录屏兜底，评委入场前先跑一次「预热失败状态」。

## 9. 心路：没有动摇，只是还没做完（口述）

问「中间有没有怀疑过方向、觉得做不完」时，回答很短：
