## 二、行为变化（需要知道的）

1. **空输入不再产生任何 API 调用。** 改造前 `judge("")` 会走完三个模块（模块内部短路）后，再走 `report_generator` 的一次大模型调用——真实上游下实测 4.27s。契约里"空输入 0 次 API 调用"只覆盖三个模块，报告那一次是漏网的。
2. **关缓存（`LLM_CACHE_MAX=0`）不再连带关掉 single-flight。** 改造前 `call()` 在缓存关闭时直接 `produce()`，4 个并发同请求会打成 4 次；现在仍只算 1 次，只是失去跨请求复用。
3. **失败路径不再放大。** 100% 5xx 下，两次相同调用从 **6 次 HTTP 降到 4 次**（原来超时会先回落一次"去掉关闭思维链参数"，与 `max_retries` 叠乘）。
4. **时限预算更紧。** 单次尝试超时不再有 1.0s 的硬下限（改为 `LLM_MIN_ATTEMPT_S`，默认 0.25s），且 single-flight 的等待者不再在预算耗尽后空等 30 秒。
5. **classic 的返回多了 `degraded_components`**（哪些组件不可用、报告是否走了本地模板回退），`/api/health` 多了 `llm{}`——都是**新增字段，向后兼容**。
6. **档位语义没有变。** 没有采用"分桶后再判档"：向下取整到 2 的倍数会把有效档位线从 5/7 左移到 4/6 与 6/8（7 分不再算"高度疑似"），那属于产品口径变更；而且 `speech_tier 用原始分、与 core_judge 逐条等价` 是既有契约（`tests/test_stability_config.py:205` 锁定）。这里改用**边界复核**：分数落在 4.5–5.5 或 6.5–7.5 时，用 `use_cache=False` 取一个独立样本，两者取中位数再判档——阈值 5/7 原样保留，只是边界不再因 1 分抖动翻档。
7. **瞬时故障不再让提供方永久失去"关闭思维链"参数。** 改造前 `except Exception` 会把 5xx/超时/DNS 都当成"参数不支持"并永久记忆；现在只有 4xx 参数类错误才回落并标记。

### 3.4 仍然存在的、已知的取舍

- **时限预算仍会有小幅超支**：预算现在按"每次尝试"执行，但每次 HTTP 尝试本身有建连/拆链开销。实测 `JUDGE_DEADLINE_S=6` + 上游连上不回时返回 7.52s（约 +25%，来自 6 次尝试的开销），远好于改造前的 515.8s，但**不是严格 ≤ 预算**。
- **边界复核只对贴着档位线的样本生效**，且用 2 个样本的中位数——能大幅降低翻档，但不是数学上消除。
- **`matrix` 的 2/4 档延迟仍为 0**：这是检验脚本自身在同一进程里连续跑模式导致的缓存命中（已在报告 §7.3 记录为"结论要打折"项），不是产品缺陷。
