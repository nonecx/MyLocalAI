# 修复说明（2026-10-15 · 第二轮）

本文件记录针对 `docs/检验报告-2026-10-15.md` 所提 13 项优化方案的代码改动、验证方式与残留。
该报告是只读检验（未改仓库）产出的，本轮把其中的 P0 全部修掉、P1 修掉三项，其余写明取舍。

## 一、P0 修复

### ⑫ 孤立代理项让三个组件抛未捕获异常，且能从外部入口触发（唯一未通过的闸门）

**改动**：

- 新增 `shared_core/text_safety.py`：`has_surrogates()` / `sanitize_text()`（代理项 → U+FFFD）。
- `shared_core/llm_client.py`：
  - `_cache_key()` 的 `blob.encode("utf-8")` 前先 `sanitize_text()` 并 `errors="replace"`
    （崩溃点原本就在这一行，且在 `chat_json`「保证永不抛异常」的承诺**上方**）；
  - `_chat_raw()` 进入缓存键与上游调用前规整 `user_text`；
  - `chat_json()` / `chat_text()` 外层加兜底 `try/except`，把任何异常转成 error 返回值
    ——「永不抛异常」这句承诺从此是被代码保证的，不只是注释。
- `rumor_agent/agent.py`：`analyze()` 入口 `sanitize_text()`，组件拿到的一定是可编码文本。
- `my_website/app.py`：`/api/analyze` 对含代理项的输入直接回 **400**（用户输入问题，不是服务端 500），
  且不再把内部异常类型/偏移量回给调用方。

**验证**：

| 检查 | 结果 |
| --- | --- |
| `harness.py edge --level 4` | `crashed_cases: []`、`unhandled_exceptions: []`、崩溃率 0（修前崩 `lone_surrogate`） |
| 三个组件对 `"ok\ud800bad"` | 正常返回（旧：三条 `UnicodeEncodeError`） |
| `_cache_key("s", bad, ...)` | 正常返回 hash |
| 网站入口 | HTTP 400（旧：500，且响应体泄露异常类型与偏移量） |
| `RumorAgent` 全链路 | 无降级组件、结果可 `json.dumps`（MCP/网站同路径） |
| 新增回归测试 | `TestSurrogateSafety`（6 个用例） |

### ⑩ 配置写坏就崩，或静默把官方来源降级

**改动**（`rumor_agent/rules.py` + `rumor_agent/sources.py`）：

- `rules.validate_sources_shape()`：合并后对已知结构做契约校验——`tiers` 的值必须是域名列表
  （某个档位写坏就退回内置默认，**不整段丢**）、`official_sites`/`commercial_sites` 必须是字典、
  档位角色与渠道权重必须是字符串列表/数字表、`unknown_kind` 必须是字符串；不合规的段退回内置默认
  并写进 `load_warnings()`（每次校验前先清掉上一轮的形状告警，保持"只反映当前环境"的契约）。
- `sources.py`：`OFFICIAL_SITES`/`COMMERCIAL_SITES` 改为带 `isinstance` 保护的取值
  （原 `dict(_REGISTRY.get("official_sites") or {})` 在 import 期强制转型，列表输入会直接 `ValueError`
  让整个 Agent/CLI 起不来）；`_load_domain_tiers()` 对非列表值跳过。

**验证**（两份坏配置原样复现）：

| 坏配置 | 修前 | 修后 |
| --- | --- | --- |
| `official_sites` 写成列表 | `import rumor_agent.tools` → `ValueError`，Agent/CLI 起不来，告警为空 | import 正常；`gov.cn`/`who.int` 仍判官方；告警：`official_sites 必须是字典（得到 list），已整段退回内置默认` |
| `tiers` 的值写成字符串 | `gov.cn`/`who.int` → 「未知来源」，无任何告警 | 该档退回内置默认；`gov.cn`/`who.int` 仍判「官方权威」；告警：`tiers 段存在不合规档位：官方权威（值不是字符串列表，已退回内置默认）` |

新增回归测试 `TestConfigShapeContract`（3 个用例）。

### ⑪ 一条回退验收会被缓存掩盖成假通过

**改动**：`tests/run_module_tests.py` 的强制回退段在 monkeypatch 前先 `llm_cache.clear()`，
并把回退后的缓存统计写进结果（`report_fallback_cache`），使"这次确实发生了一次失败调用"可核对。

**验证**：实跑该脚本 —— `回退后缓存统计: {'entries': 0, 'hits': 0, 'misses': 1}`、
`含'本地模板回退': True`。修前在有可用密钥的机器上这一步必然复用正常路径的缓存正文、真实回退 0 次。

### ④ 分桶护栏只挡住已观察到的那一个边界

**改动**：`rumor_agent/verdict.py` 的 `bucket_score` 由 `round(value/step)*step` 改为**向下归并**
`(value // step) * step`。实测抖动 6.0↔7.0 原本分到两桶，而它正好跨过 45 分阈值。

**验证**（报告里的反例原样复跑）：

| 输入 | 修前 | 修后 |
| --- | --- | --- |
| `markers=14, emotion=6.0` | 41「存疑待核实」 | 41「存疑待核实」 |
| `markers=14, emotion=7.0` | 45「疑似谣言」（**跨档**） | 41「存疑待核实」（同档） |
| `markers=20, emotion=8.0` / `9.0` | 51 / 51（同档） | 51 / 51（同档） |

代价写进了 docstring：桶边界左移到 5↔6、9↔10，进一步靠调用侧缓存兜底。

## 二、P1 修复

### ⑤ 失败路径上 single-flight 被放大

**改动**（`shared_core/llm_cache.py`）：`_INFLIGHT` 从 `key -> Event` 改为
`key -> {event, value, error, accepted}`。等待者等的是"结果或失败"，leader 失败时把同一份失败结果
（或异常）共享给等待者，只有等超时（首位仍未返回）才自己 `produce()`。

**验证**（离线复现）：

| 场景 | 修前 | 修后 |
| --- | --- | --- |
| 4 线程同 key、produce 返回 `('', 'API 调用失败…')` | `produce` 调用 **4** 次 | **1** 次，4 个结果一致 |
| 6 线程同 key、leader 抛异常 | 各自重跑 | **1** 次，6 个线程都拿到同一异常 |

新增回归测试 `TestTransportRobustness`（前两个用例）。

### ⑥ 请求级预算不跨线程

**改动**：`llm_cache` 新增 `deadline_scope_at(absolute_at)` 与 `deadline_at()`；
`rumor_agent/agent.py` 的 Agent 工作线程与 6 个补算线程都套上主线程传来的绝对截止时刻。
（`_DEADLINE` 是 `threading.local`，子线程原先完全看不到主线程的预算。）

**验证**：主线程 `deadline_scope(0.1)` 过期后 —— 不继承时子线程 `budget_exhausted()=False`、
`attempt_timeout(30)=30`；继承后 `True` / `1.0`。新增回归测试 `TestTransportRobustness` 第三个用例。

### ③ 备用链路对 Agent 完全无效

**改动**（`rumor_agent/llm.py` + `shared_core/llm_client.py`）：新增
`first_available_provider()` / `provider_spec()`；`build_llm()` 改为按主提供方→`LLM_FALLBACKS` 顺序
取第一个配了密钥的提供方建 `ChatOpenAI`，且 `extra_body`（关思维链）**只发给 LongCat**（原先无条件附带）。
`mcp_server` 的文档字符串同步改为不写死 LONGCAT（`analyze_rumor` / 模块头）。

**验证**：本机（只配 LongCat）`build_llm()` 仍返回 `ChatOpenAI`（默认路径未受影响）；
把主提供方密钥置空后，`first_available_provider()` 会按 `LLM_FALLBACKS` 返回第一个配了密钥的提供方
（现成的 `tests/test_stability_config.py::TestProviderBinding` 覆盖提供方三项同改、错配报错、
LongCat 专有参数不外发；备用链路对 classic 那条路径的端到端验证见同文件的
`test_fallback_chain_is_used_when_primary_is_down`）。**按报告建议的"置空主提供方密钥 + 备用可用"整链
实跑未做**——本机没有第二家提供方的密钥，这条只能做配置层验证，如实记在这里。

**顺带修掉的三处测试自身毛病**（不改被测行为，只让断言测的是它命名的那件事）：

1. `test_backfill_threads_are_daemon_and_parallel`：原来用墙钟 `elapsed < 0.35s` 判断"并行"，
   机器一忙（本轮复现：与另一个 Python 进程同时跑时 1.13s）就假红。改成**四方屏障**——
   四个组件都在屏障上等齐才算并行，串行执行必然超时。
2. `TestTransportRobustness` 的两个用例：原先直接起 4 个线程就断言"只调一次 produce"，
   线程调度慢时首位已经算完、后续线程走的是缓存命中路径，测不到失败共享。改为一同起跑 +
   首位悬停等释放，把时序钉死。
3. `rumor_agent/llm.py` 的 `extra_body` 只发给 LongCat 后，
   `tests/test_stability_config.py::TestProviderBinding::test_thinking_param_only_sent_to_longcat`
   的原有断言仍然成立（未被削弱）。
