对象：MyLocalAI 言论分析项目（网站 + 谣言 Agent + 四模块判定）。环境：Windows 11（win32 10.0.22631）、Python 3.13.13；仓库不是 git 仓库、没有远端（`static.json`）。提供方为 longcat / LongCat-2.5-Preview（`.env` 只有 LongCat 三项配置），未配置其它提供方、未启用备用链路。

## 一、结论摘要

25 道闸门过了 24 道，唯一没过的是「边界输入不崩溃（真实 API）」：14 个边界用例里有 1 个（孤立代理项 `lone_surrogate`）让 emotion / aggression / logic 三个字段各抛一次未捕获的 `UnicodeEncodeError`；我本轮复现了同一条异常，并确认它能从网站接口和命令行两条外部入口打进来（详见 §5.5、§7.2）。功能主干是真实验到的，不是「没崩就算过」：裁判四档规则 128/128 组合、言论分层两处实现 200/200 逐条等价、信源伪装域 `xinhuanet.com.evil.com` 未被判为官方、7 条端到端案例全部命中预期档位，这些都是可复算的判定。可复现性要加限定条件：缓存开启时同输入结论与七个字段完全一致（分数极差 0），关掉缓存后 4 条文本里有 3 条 `emotion_score` 出现 ±1 抖动、1 条 `emotion_tendency` 抖动——「同输入同结论」靠的是进程内的结果缓存兜底，不是模型本身确定。抗压方面没有致命问题，但**并发与突发两组数字里有相当一部分是缓存命中的 0 秒请求**（突发 3/16、持续 6/16），剔除后 p50 从 1.869s 升到 2.464s（持续）、从 14.127s 升到 17.603s（突发），所以「并发到 4 不降级」只能读作「并发下 0 异常、0 限流」，不能读作「真实负载下延迟与吞吐健康」。真正的隐患是三处会改变结论或让结论难以追溯的地方：分桶护栏覆盖不到 `speech_tier` 导致同分翻档、配置写坏会崩溃或把官方来源静默降级、以及一条回退验收会被缓存掩盖成假通过（三点我都已复现）。整体判断：**可以用，但先修下面的 P0 四项，其中「边界输入崩溃」是唯一未通过闸门的直接原因，也是唯一能从接口直接被外部输入触发的崩溃；同时不要把「同输入必同结论」当成对外承诺。**

## 二、检验范围与方法

### 2.1 跑了哪些检查、怎么跑的

检验主体是项目自带的采集器 `.tmp/verify/harness.py`，它有 **11 种模式**（`harness.py:1164` 的 `MODES` 表：static / contract / unit / smoke / edge / determinism / concurrency / matrix / site / agent / digest）。**14 个结果文件并不等于 14 种模式**，其中 3 个是同一模式的第二次或带参调用、1 个是汇总产物。对应关系如下（每个文件的 `mode` 字段我都读出来核过）：

| 结果文件（`.tmp/verify/run-live/`） | 产生它的调用 | `mode` 字段 |
| --- | --- | --- |
| static.json | `static` | static |
| contract.json | `contract` | contract |
| unit.json | `unit` | unit |
| smoke.json | `smoke` | smoke |
| edge.json | `edge --level 4` | edge |
| determinism.json | `determinism --repeat 5 --level 4` | determinism |
| determinism_nocache.json | 同上，但子进程环境里 `LLM_CACHE_MAX=0`（关缓存对照） | determinism |
| matrix.json | `matrix --requests 4` | matrix |
| burst_judge.json | `concurrency --target judge --level 8 --requests 16`（**突发组**） | concurrency |
| sustained_module.json | `concurrency --target module --level 4 --requests 16`（**持续组**） | concurrency |
| site.json | `site --port 8031 --level 4 --requests 8 --api-mode classic` | site |
| agent.json | `agent` | agent |
| agent_fault.json | `agent --fault`（把 API 地址指向不可达端口） | agent |
| digest.json | `digest`（汇总前 13 个文件成 25 道闸门） | digest |

各模式的调用参数取自本次检验的运行脚本 `.zcode/workflow-drafts/MyLocalAI-只读检验-2026-10-15.dwf.ts:407-483`；关缓存那一档的包装见同文件 `:67-78`（`LLM_CACHE_MAX=0`）。

**汇总规则**：`digest` 只读取 static / contract / unit / smoke / edge / determinism / matrix / site / agent / agent_fault 这 10 个文件（`harness.py:929-931`）。**因此 `burst_judge.json`（突发）与 `sustained_module.json`（持续）不参与任何闸门判定**，它们与下面 §5.4 的过载保护一样，属于闸门之外的补充证据。

**派生的补充探测**（不产出 run-live 文件）：

| 补充探测 | 做了什么 | 数据据以引用 |
| --- | --- | --- |
| 同文本连跑两次 | 先 `llm_cache.clear()`，再连续 `judge` 同一段文本两次 | 脚本 `.zcode/workflow-drafts/…dwf.ts:173-195` |
| 过载保护（§5.4） | 起 uvicorn（:8037），8 个不同长文本并发打 `/api/analyze`（`mode=classic`），期间探一次 `/api/health` | 脚本 `.zcode/workflow-drafts/…dwf.ts:197-266`；本次检验数据「过载保护」段 |

**过载保测试本身是 HTTP 层的**：8 个请求同时打网站，服务端并发名额上限是 4（`my_website/app.py:55` `MAX_CONCURRENT_ANALYSES = 4`、`:112-126` 的 `_Slot` 拿不到名额就抛 503 且带 `Retry-After: 5`）。**matrix / burst / sustained 三组则是进程内直调**（`harness.py:634` 与 `:650` 分别调 `judge()` 与 `analyze_emotion()`），不经过 HTTP、也不受那 4 个名额限制。两组数字的条件不同，§5 会分开说清楚。

### 2.2 检验器自身的局限（先写在前）

1. **不是独立检验。** 采集器（`.tmp/verify/harness.py`）与被检验的实现出自同一作者，部分闸门判定用的也是同一套预设——例如四档规则的期望值在 `harness.py:300-306` 自行重写了一遍，端到端 7 条案例的期望档位写在测试脚本本身（`tests/rumor_agent_e2e.py` 的 `SAMPLES`，每条带 `expected_any_of`）。它能证明「与作者自己的预期一致」，不能证明「与外部标准一致」。
2. **部分闸门读的是离线构造的值。** 例如报告回退闸门（`harness.py:285-295`）直接调 `generate_report` 并传入固定的 emotion/attack/logic，不是真的让上游失败一次。
3. **本轮我没有重跑整套。** `agent` / `edge` / `site` 等联网模式的执行结果来自本次检验数据；我复现的是报告中明确标注「本轮复现」的那几项（孤立代理项异常路径、失败路径 4 次调用、`bucket_score` 表、两处档位翻档、两份坏配置、缓存掩盖回退断言、以及几条外部入口的崩溃探测）。
4. **三视角发现里各有 1 条只做了评审、未安排独立复核**（`复核备注`：泛用性、稳定性、功能性各第 3 条），报告中凡引用它们的地方都标了「未独立复核」。

### 3.3 关键阈值（此前缺，读者无法核对档位）

档位判定口径来自 `rumor_agent/verdict_rules.json`，模块常量在 `rumor_agent/verdict.py:45-47`：

核对「78 分＝高风险档」：本轮实跑 `_label_for(78)` 返回「高风险谣言」（high=70），所以那条闸门的通过证据成立。

**端到端 7 条案例的「预期档位」出自哪里**：写在测试脚本本身（`tests/rumor_agent_e2e.py` 的 `SAMPLES`，每条 `(id, text, expected_any_of)`），例如 `rumor_poison` 接受 `('高风险谣言','疑似谣言')`、`pure_insult` 只接受 `('无可核实陈述',)`。也就是说，这是**作者自己写的期望集合**，不是外部标注的黄金集；判据是「实际标签 ∈ 期望集合」。这一点与我 §2.2 的自我限定一致。

**降级后档位可以变，为什么仍算 PASS**：`agent_fault` 两条案例的期望集合与正常运行时是同一套，`rumor_poison` 期望 `('高风险谣言','疑似谣言')`，实际 45 分「疑似谣言」落在集合内，因此 `match=True`（`tests/rumor_agent_e2e_results_fault.json` 每条都带 `expected_any_of` 与 `match`）。**结论是：这道闸门验的是「故障时仍能给出一个预期范围内的结论」，不是「故障时档位不变」。** 参照 §5.6 的 91→45，档位确实会变，这只是不被判失败而已。

### 3.4 逐条说明：哪些真把功能验到了，哪些只是没崩

**只是「没有崩」或证据强度不足，需要打折看：**

- **并发到 4 不降级**：见 §5.1，2/4 两档是缓存命中形态，该闸门实际证明「并发下 0 异常、0 限流、结果仍给出」。
- **同输入结论可复现**：通过的是有缓存那一版；关缓存后同批文本出现字段抖动（§4.1）。

## 四、稳定性（同输入可复现）

### 4.1 缓存开启与关闭的对照

同一批文本各重复 5 次，逐字段看是否漂移（来源：`determinism.json` 与 `determinism_nocache.json`）。

**缓存开启：**

| 文本 | 重复 | 漂移字段 | 稳定字段数 | 分数极差 | 结论取值 | 降级次数 |
| --- | --- | --- | --- | --- | --- | --- |
| insult | 5 | 无 | 7 | 0 | 高度疑似水军/煽动性言论 | 0 |
| rational | 5 | 无 | 7 | 0 | 情绪化宣泄/普通网络争论 | 0 |
| review | 5 | 无 | 7 | 0 | 情绪化宣泄/普通网络争论 | 0 |
| rumor | 5 | 无 | 7 | 0 | 疑似情绪化谣言 | 0 |

**缓存关闭（`LLM_CACHE_MAX=0`）：**

| 文本 | 重复 | 漂移字段 | 稳定字段数 | 分数极差 | 结论取值 | 降级次数 |
| --- | --- | --- | --- | --- | --- | --- |
| insult | 5 | emotion_score（10.0 与 9.0） | 6 | 1 | 高度疑似水军/煽动性言论 | 0 |
| rational | 5 | emotion_score（0.0 与 1.0）、fallacy（「无」与「未知」） | 5 | 1 | 情绪化宣泄/普通网络争论 | 0 |
| review | 5 | emotion_score（2.0 与 3.0） | 6 | 1 | 情绪化宣泄/普通网络争论 | 0 |
| rumor | 5 | emotion_tendency（三种取值） | 6 | 0 | 疑似情绪化谣言 | 0 |

这四条文本在 5 次重复内**结论档位没有变**，抖的是中间字段。另有两条独立观测：同文本连跑两次，第一次 18.74s、第二次 0s，结论与 `emotion_score` 一致、报告长度都是 474 字、缓存 entries 4 / hits 4 / misses 4；契约模式里同入参重复 20 次，取值只有 1 种（疑似谣言 66）。

**为什么「分数没动、倾向却三种」——两者是并列字段，不是派生关系。** `emotion_tendency` 与 `emotion_score` 都直接来自模型那一次 JSON 输出，各自独立校验后返回：`module_language/language_module.py:78` 定义倾向白名单 `{冷静客观, 积极宏观, 情绪化宣泄, 极度负面, 恶意辱骂}`，`:117-118` 把不在白名单的值落回哨兵「未知」，`:121` 单独处理分数（`_safe_score`）。所以派生的只有分数：`verdict.py:172` 的计分只读 `emotion_score`（并按步长 2 归并），`verdict.py:99-105` 的分层读 `emotion_score` 与 aggression/relevance，**计分与分层都不读 `emotion_tendency`**；倾向只用于展示（`report_generator.py:97、111、116`）。因此「score 钉在 9.0 而 tendency 在三种取值间摆动」在实现上是完全可能的：分数单调、另一个独立字段随机。

### 4.2 可复现靠什么兜底，什么时候会失效

**兜底是进程内的结果缓存**，没有第二道保险。`shared_core/llm_cache.py:26` 是模块级字典 `_ENTRIES: Dict[str, Tuple[float, Any]] = {}`；键由 `shared_core/llm_client.py:342-347` 生成，内容是「提供方 + 地址 + 模型 + 系统提示词 + 用户文本 + 温度 + max_tokens + enable_thinking」的哈希。同一段提示词打出去就返回上次的答案，模型不再参与。

**这个兜底在下列情形会失效，结论回到漂移状态：**

1. **进程重启**：`_ENTRIES` 只在内存里，没有落盘或跨进程共享代码。
2. **多进程 / 多 worker 部署**：每进程一份缓存，请求落到不同 worker 就是不同答案。
3. **TTL 到期**：默认 900 秒（`llm_cache.py:32`，`LLM_CACHE_TTL_S`）。
4. **条数淘汰**：默认上限 256 条，超出后按「最早过期优先」淘汰（`llm_cache.py:41`、`:50`）。
5. **失败不入缓存**：`llm_client.py:371-373` 的 `accept` 拒绝带错误的返回值，失败那次白打，下次重来。
6. **检索层不受缓存覆盖（最容易被忽略）**：证据收集每轮现打 `search_fn(q, 6)`（`rumor_agent/evidence.py:431`），`rumor_agent/search.py` 没有缓存，只有 URL 去重与排序。缓存键是「条目拼成的提示词」，条目本身不被缓存；两次运行搜到不同条目 → 不同提示词 → 不同键 → 立场判定与抬分全部重算。`已知未覆盖` 也把这条单列：**「检索层抖动本身没有被消除，只被观测」**。

**方法层面的坑：** `tests/test_stability_config.py:282-290` 那条名为「端到端结论一致」的验收，把 emotion/attack/logic 作为参数直接传入并 mock 掉 `generate_report`，整条测试没触碰 LLM。它验的不是它命名的那件事。

### 5.5 边界输入

14 个用例，崩溃 1 个，崩溃率 0.071，崩溃用例名单 `['lone_surrogate']`。未崩的 13 个（空、纯空格、换行制表符等）走短路，返回带 error 的默认值且 0 次 API 调用。

> `UnicodeEncodeError: 'utf-8' codec can't encode character '\ud800' in position 476: surrogates not allowed`（emotion；位置 370、690 分别为 aggression、logic）

**这三个数字是「被 utf-8 编码的那个字符串里的字符偏移量」，不是行号、也不是栈帧深度。** 我本轮把它定位到了具体字串：缓存键是把 `[提供方, 地址, 模型, 系统提示词, 用户文本, 温度, max_tokens, enable_thinking]` 整体 `json.dumps(..., ensure_ascii=False)` 后做 sha256（`llm_client.py:342-347`），我把 emotion/aggression/logic 三个系统提示词分别代入重算，代理项恰好落在第 **476 / 370 / 690** 个字符上（三个字串总长 499 / 393 / 713）。这与报错里的 position 完全一致。

崩溃点就是 `shared_core/llm_client.py:347` 的 `blob.encode("utf-8")`（由 `:368` 调用）。本轮复现路径与外部可达性见 §7.2。

## 六、优化方案

### 6.1 泛用性

**① 档名以中文字符串字面量写在 Python 里，换行业会静默失效**

- 现状与证据：`rumor_agent/search.py:47` `_FETCH_TIERS = frozenset({TIER_OFFICIAL, "权威媒体/辟谣平台", TIER_PORTAL})`；`rumor_agent/browser.py:29` `LINK_TIERS` 同形；`rumor_agent/sources.py:32` 把 `TIER_MEDIA` 硬编码为 `"权威媒体/辟谣平台"`，`:36` `RELIABLE_TIERS`；`rumor_agent/opinions.py:37` `CHANNEL_SCORE` 也以这四个中文档名为键（以上均本轮读源码确认）。评审给出的实测：把 registry 换成新行业档名后，`classify` 认得新档名，但 `source_kind` 返回「其他」、`fetch_tiers` 为 False，且不报错。
- 建议：把「可靠档 / 可抓档 / 可扩链档 / 渠道权重」也做成 JSON 配置，或按 `tiers` 声明顺序取前 N 档，不要用档名字面量做成员判断。
- 优先级：**P1**（当前部署不受影响；一旦按 README 换行业就会静默出错）。
- 验证检查：准备一份改名后的 registry，断言 `classify_domain`、`source_kind`、`_FETCH_TIERS`、`LINK_TIERS`、`RELIABLE_TIERS` 对同一域名给出一致结论，并把它加为常驻契约闸门。

**② 「只改 JSON 就能换判定标准」的承诺只兑现了一部分**

- 现状与证据：`rumor_agent/verdict_rules.json` 的键只有 `['_comment','thresholds','no_claim_risk_cap','_no_claim_risk_cap_comment','evidence_lift','stability']`（本轮实读）；话术权重在 `rumor_agent/patterns.py:74-75`（`MARKER_CAP=45` / `CREDIBILITY_CAP=15`）与 `:130-131`，logic/claims 计分系数在 `rumor_agent/verdict.py:177-180`，四档规则在 `core_judge.py:90-97` 与 `verdict.py:94-105` 各写一遍，档位标签与枚举在 `verdict.py:22-28` 等处的 Python 里。README.md:68 的说法覆盖了阈值/封顶/抬分锚点/稳定性护栏，未覆盖权重与规则本身。
- 建议：把话术权重、logic/claims 系数、档位标签与枚举纳入 `verdict_rules.json`，让 `core_judge` 与 `verdict.speech_tier` 共用同一份规则（现在靠 200/200 网格保证等价，是「两处各自正确」而非「一处定义」）。
- 优先级：**P1**。
- 验证检查：改 JSON 权重后断言分数随之变化；把 200/200 等价性网格扩到新字段。

**③ 备用链路对 Agent 完全无效**（评审提出，**未独立复核**）

- 现状与证据：备用链路的唯一实现点在 `shared_core/llm_client.py:385-418`；`rumor_agent/llm.py:22-38` 只用 `get_api_key()/get_model()/get_base_url()` 读主提供方，并在 `:37` 对所有提供方无条件发送 `extra_body={"chat_template_kwargs":{"enable_thinking": False}}`。
- 建议：`build_llm` 也走提供方表与备用链，`extra_body` 按提供方决定是否附带。
- 优先级：**P1**。
- 验证检查：把主提供方密钥置空、备用密钥可用，断言 Agent 仍能出结论。

### 6.2 稳定性

**④ 护栏是点状的，而且 speech_tier 根本不吃护栏（P0）**

- 现状与证据：`rumor_agent/verdict.py:172` 只对 `emotion_score` 做分桶，`:99-105` 的 `speech_tier` 用原始分数与原始 `aggression` 字符串。本轮实跑：
  - `bucket_score` 表为 `0,1→0; 2→2; 3,4,5→4; 6→6; 7→8; 8,9→8; 10→10`——9↔10 不归并，7↔8 跨桶。
  - `V.assess({'marker_points':14}, {'emotion_score':6.0}, {'aggression_level':'中'}, {'logic_relevance':'弱'}, {'has_factual_claim':True})` → **41「存疑待核实」**；只把 `emotion_score` 改成 7.0 → **45「疑似谣言」**，正好跨过 45 分门槛。
  - 固定 `markers=20`、`emotion_score=8`，`aggression` 取「高」与「中」时 `risk_score` 都是 **51**，但 `speech_tier` 从「高度疑似水军/煽动性言论」变成「疑似情绪化谣言」。
  - 这不是假想：关缓存后实测就出现过 `emotion_score` 9.0↔10.0 的抖动，而 9 与 10 落在不同桶。
- 建议：对参与判定的每个离散阈值量（至少 aggression 的高/中、logic_relevance 的强/弱）做同粒度归并或加滞回；`speech_tier` 改用归并后的量；把阈值挪到远离整数抖动点的位置。
- 优先级：**P0**（同一份中间结果会产出不同档位＝结论错误）。
- 验证检查：对每个阈值上下各 ±1 的整数逐点跑 `assess`，断言档位不跨边界。

**⑤ 失败路径上 single-flight 被放大（P1）**

- 现状与证据：`shared_core/llm_cache.py:119-127` 在 `finally` 里先 `_INFLIGHT.pop` + `event.set()`，之后才判 `accept(value)`（`:125`）；等待者醒来 `get` 仍 miss，各自 `produce()`。本轮复现：4 线程同键、`produce` 返回 `('', 'API 调用失败: ConnectionError')` → **`produce` 被调用 4 次**。
- 建议：leader 失败时把错误/None 共享给等待者，或对失败做短 TTL 负缓存。
- 优先级：**P1**。
- 验证检查：断言失败场景下 `produce` 只被调用 1 次。

**⑥ 请求级预算不跨线程**（评审提出，**未独立复核**，P1）

- 现状与证据：`shared_core/llm_cache.py:154` `_DEADLINE = threading.local()`；`rumor_agent/agent.py:166-167` 在工作线程里跑 `_run_agent`，工具链的 `chat_json` 都在该线程执行，看不到主线程设的预算。评审实测主线程 `deadline_scope(0.1)` 过期后子线程仍为未过期。这与 `agent.py:189-191` 注释里「整个分析共用一个总预算」的说法不符。
- 建议：把 deadline 作为显式参数传进工具层，或在线程创建时继承；否则改文档。
- 优先级：**P1**。
- 验证检查：用一个必然超时的上游，断言总耗时仍在 `deadline_s` 内。

**⑦ 组件结果没有持久化或跨进程共享（P1）**

- 现状与证据：见 §4.2 六类失效条件；缓存键是提示词而非条目（`llm_client.py:342-347`），检索层每轮现搜（`evidence.py:431`）。
- 建议：按「文本哈希 + 规则/提示词版本」把组件结果（至少证据本条目与立场）持久化或进程外共享；若坚持进程内，就在 API 与 README 里把可复现范围写明为「同一进程、TTL 内、且检索到同一批条目」。
- 优先级：**P1**。
- 验证检查：开两个独立进程、或在关缓存条件下跑同一条文本，断言结论与分层一致（这条现在必然失败，正好当验收靶子）。

**⑧ 单次分析偏慢（P2）**：全链路并发 1 时 p50 14.01s；网站并发 4 时 p50 18.102s、p95 28.986s；过载时被放行的 4 个请求 16.2–21.8s。属体验与容量问题，不要为提速牺牲确定性护栏。验证检查：同批文本记录 p50/p95，改动前后对比。

**⑨ 检验器与实现同源，缺外部参照（P1）**：见 §2.2。建议为核心承诺（同输入同结论、证据抬分、信源分级）准备固定证据集与独立断言。验证检查：用固定证据集跑同一文本，断言证据条目集合与判定一致，且不依赖任何缓存。

### 6.3 功能性

**⑩ 配置写坏就崩，或者静默把官方来源降级（P0）**

- 现状与证据：`rumor_agent/rules.py:99-125` 的 `_load` 只做深合并不校验类型，`rumor_agent/sources.py:45` 在 import 期执行 `dict(_REGISTRY.get("official_sites") or {})` 强制转型，`sources.py:51-56` 会把字符串当域名列表逐字符迭代。本轮实测两份坏配置：

**⑪ 一条回退验收会被缓存掩盖成假通过（P0）**

- 现状与证据：`tests/run_module_tests.py:280-282` 先用同一组 `SAMPLE_*` 参数跑正常报告，`:329-335` 再把 `create_client` 打成 `None` 跑同一组参数，`:342-343` 检查「本地模板回退」标记。缓存键不含「客户端是否可用」（`llm_client.py:342-347`），命中即返回旧值（`llm_cache.py:96-99`）。本轮复现：第一次成功入缓存后，第二次即使 `produce` 返回失败，仍返回缓存里的成功正文，**真实调用 0 次**。配了可用密钥时这一步必然假通过。
- 建议：回退验收前先 `shared_core.llm_cache.clear()`（或临时置 `LLM_CACHE_MAX=0`），并断言「这一次确实发生了一次失败的调用」。
- 优先级：**P0**（它让一条检验结论本身错了：把没验到的路径报成验到了）。
- 验证检查：重跑该步骤，同时断言「含回退标记」与「真实调用失败 1 次」；只满足前者即失败。

**⑫ 孤立代理项让三个组件抛未捕获异常，且能从外部入口触发（P0，唯一未通过闸门的直接原因）**

- 现状与证据：崩溃点是 `shared_core/llm_client.py:347` 的 `blob.encode("utf-8")`；该行在 `_chat_raw`（`:368`）里、位于 `chat_json`（`:421-442`）声称「调用方据此返回默认值字典 + error 键，保证永不抛异常」的**上方**，所以异常根本没有被转成 error 键。
- 我从外部入口逐条探测（本轮实跑）：
  - **网站 `POST /api/analyze`，mode=classic**：HTTP **500**，响应体还是 `{"detail":"分析链路异常: UnicodeEncodeError: 'utf-8' codec can't encode character '\\ud800' in position 476: surrogates not allowed"}`——不但崩，还把内部异常类型、编解码器与偏移量回给了调用方（信息泄露）。
  - **网站 `POST /api/analyze`，mode=agent**：HTTP **500**（`Internal Server Error`）。异常发生在响应序列化阶段：`PydanticSerializationError: Error serializing to JSON: UnicodeEncodeError ... in position 2`——因为记录里回显了原始文本（`my_website/app.py:196` 的 `"text": text`）。也就是说 agent 模式的分析本身容错（见下一条），但**回显原文**这一句把请求带崩了。
  - **`python -m rumor_agent --json <文本>`**：退出码 **0**，正常给出结论。原因在 `rumor_agent/state.py:99-105`：组件抛的异常被兜住并记成 `{"error": "组件异常: UnicodeEncodeError: ..."}`，`verdict.py` 把带 error 的组件记为降级，最终输出「无可核实陈述/风险分 0/置信度低」。输出里 `text_preview` 的代理项被替换成 `?`。
  - **`python main.py --text <文本>`**（经典判定路径，不经 Agent 兜底）：退出码 **1**，栈顶同样是 `llm_client.py:347`，等于直接崩在命令行。
  - **MCP `analyze_rumor`**：函数本身返回字符串（含 `evidence_book.claim` 等原文字段），我实测该字符串**无法按 utf-8 编码**（`'\ud800' ... position 462`）。真实 MCP 客户端下的表现取决于 SDK 的序列化方式，我没有接真实客户端，**未验**（见 §7.1）。
- 建议：在进入缓存键与判分之前把文本规整为可编码的字符串（例如先 `text.encode('utf-8','replace').decode('utf-8')` 或拒绝含孤立代理项的输入），并在 `_chat_raw` 外层兜住 `UnicodeEncodeError` 转成 error 键，保证 `chat_json` 的「永不抛异常」承诺成立；网站侧对不可编码输入返回 400 而不是 500，且不要把内部异常详情回给调用方；`/api/analyze` 记录里回显原文时同样先规整。
- 优先级：**P0**（未捕获异常＝崩溃，且是唯一能从外部输入直接触发的崩溃；同时命中唯一未通过的闸门）。
- 验证检查：把 `edge` 模式再跑一次，断言 `unhandled_exceptions` 为空、`crashed_cases` 为空；另加三条用例——`/api/analyze` 对同文本返回 400 而非 500、`main.py --text` 退出码为 0、MCP 返回串可 utf-8 编码。

**⑬ MCP 静默截断 4000 字且不回传截断标志（P2）**

- 现状与证据：`rumor_agent/agent.py:59` `DEFAULT_MAX_CHARS = 4000`，`:182-183` 截断；`rumor_agent/mcp_server.py:141-142` 的 `open_evidence_session` 直接切到 4000 且不说明，`:191-195` 的 `analyze_rumor` 返回白名单不含 `truncated` / `text_preview`（以上本轮读源码确认）；网站侧把上限抬到 8000 并回传 `truncated`（`my_website/app.py:218`）。**评审给出的 mock 结果我未独立复核。**
